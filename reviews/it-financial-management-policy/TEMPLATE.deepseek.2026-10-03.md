# DeepSeek Review — POL-FIN-001 TEMPLATE

# Замечания к шаблону POL-FIN-001

## 1. CAPEX/OPEX классификация — критичные пробелы (раздел 4.1)

**1.1. Порог CAPEX не соответствует ФСБУ 6/2020.** С 2023 г. лимит для ОС устанавливается организацией самостоятельно, но по ФСБУ 6/2020 п.5 есть обязательные критерии признания (материальный объект, срок использования >12 мес., способность приносить экономические выгоды). Формулировка «стоимостью свыше {{ПОРОГ_КАПЕКС}}» без указания срока полезного использования и без ссылки на учётную политику по ФСБУ 6/2020 некорректна. Нужно: «признаётся ОС при одновременном соблюдении критериев п.5 ФСБУ 6/2020 и стоимости свыше {{ПОРОГ_КАПЕКС}}, установленного учётной политикой».

**1.2. Нет ссылки на ФСБУ 14/2022 (НМА).** ПО и капитализируемая разработка — это НМА. Шаблон вообще не упоминает ФСБУ 14/2022, хотя именно он регулирует:
- признание прав по лицензионным договорам (п.4-7);
- различие между НМА и правами по лицензиям (неисключительная лицензия ≠ НМА);
- учёт «сложных» объектов (сайты, ПО как единый объект).

**1.3. Ошибка: «ПО по perpetual license = CAPEX».** По ФСБУ 14/2022 неисключительная лицензия на ПО **не признаётся НМА** — это расходы будущих периодов (РБП), списываемые равномерно. В НМА попадает только исключительное право. Формулировка в шаблоне приведёт к искажению отчётности. Нужно разделить: исключительные права → НМА; неисключительные лицензии → РБП (сч. 97), независимо от срока.

**1.4. Не учтён ФСБУ 26/2020 (капвложения).** Для капитализируемой разработки и дооборудования нужны ссылки на ФСБУ 26/2020 — какие затраты включаются в капвложения (зарплата разработчиков, услуги подрядчиков, тестирование), а какие нет (обучение, реклама, поддержка после ввода).

**1.5. Налоговый учёт (НК РФ) не отражён.** В шаблоне нет:
- ссылки на ст. 257 НК РФ (амортизируемое имущество, первоначальная стоимость от 100 000 ₽ — порог, отличный от бухгалтерского);
- ст. 264 п.1 пп.26 (расходы на ПО и БД — прочие расходы);
- ст. 262 (расходы на НИОКР);
- п.1 ст. 172 и ст. 171-172 (НДС по лицензиям, особенно импортным);
- **налоговый учёт ПО из реестра российского ПО (ст. 257 п.4, повышающий коэффициент 2 к расходам на НМА из реестра)** — критично для IT-компаний.

**1.6. Не описана амортизация.** Для CAPEX-объектов нужны: срок полезного использования, метод (линейный/нелинейный), момент начала амортизации, ликвидационная стоимость (ФСБУ 6/2020 п.30-31). Без этого классификация CAPEX бессмысленна.

**1.7. Не учтены облачные/гибридные модели.** «SaaS = OPEX» — упрощение. При долгосрочных предоплаченных контрактах (3-5 лет) и существенных суммах возникает вопрос РБП и дисконтирования (ФСБУ 25/2018 для аренды, если это выделенные ресурсы). Нужен критерий: срок, сумма, наличие выделенного оборудования.

## 2. Бюджетирование — неполнота (раздел 5)

**2.1. Нет этапа утверждения бюджета.** §5.1 — подача заявки, §5.3 — корректировки. Пропущено: кто утверждает, в какой срок, что происходит при отклонении, есть ли защита бюджета перед комитетом.

**2.2. Нет связи со стратегией и портфелем проектов.** Бюджет формируется «по статьям», но нет требования привязки к IT-стратегии, roadmap, портфелю проектов. Для IT-финансов это ключевой разрыв — без этого бюджет превращается в смету.

**2.3. Нет процесса приоритизации.** Что делать, если заявок больше бюджета? Нужны критерии (ROI, TCO, риск, соответствие архитектуре) и орган принятия решений (IT-комитет / инвестиционный комитет).

**2.4. Нет сценариев.** Для IT-бюджета стандарт — 3 сценария (базовый/оптимистичный/пессимистичный) или минимум «базовый + стресс». Не упомянуто.

**2.5. Нет помесячного/поквартального профиля.** Бюджет «на год» без разбивки по периодам не позволяет контролировать cash flow. Особенно критично для лицензий с годовыми платежами и облака (monthly billing).

**2.6. Нет связи с закупочным планом.** Бюджет и план закупок должны синхронизироваться (сроки тендеров, длинные циклы поставки оборудования). В шаблоне эти процессы разорваны.

**2.7. Резерв — только «согласуется с ФД».** Не указано: лимит использования без согласования, кто может инициировать, как восполняется, что если резерв исчерпан.

**2.8. Нет метрик исполнения.** Не определены KPI: budget variance, forecast accuracy, % OPEX/CAPEX, cost per user, cloud spend vs plan. Без метрик §5.4 — просто отчёт, а не управление.

## 3. Управление лицензиями — существенные пробелы (раздел 3, 4.2)

**3.1. Лицензионный реестр только упомянут в терминах.** Нет процедуры: кто ведёт, как часто актуализируется, какие поля (вендор, SKU, метрика лицензирования, срок, кол-во, стоимость, ответственный), где хранится.

**3.2. Нет процессов SAM (Software Asset Management).** Отсутствуют:
- инвентаризация установленного ПО (сверка с реестром);
- контроль использования (usage monitoring) — критично для оптимизации;
- выявление неиспользуемых лицензий (reharvesting);
- управление «true-up» у вендоров (Microsoft, Oracle, SAP) — риск доначислений.

**3.3. Нет процедуры продления.** Что происходит за N дней до истечения? Кто отвечает? Что если продление пропущено (риск остановки бизнеса)?

**3.4. Нет управления compliance-рисками.** Аудит вендора, несоответствие лицензионным метрикам (например, использование SQL Server Enterprise вместо Standard), ответственность за нарушения.

**3.5. Не учтены особенности российского рынка.** С 2022 г. — принудительное лицензирование ПО ушедших вендоров (Постановление Правительства РФ № 299 от 29.03.2022 и последующие), параллельный импорт, реестр российского ПО. Шаблон этого не отражает.

**3.6. Нет связи с §4.1.** Не указано, как тип лицензии (perpetual/subscription/usage-based) влияет на CAPEX/OPEX и на бюджетирование.
