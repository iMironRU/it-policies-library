# Как контрибьютить

Спасибо за интерес к проекту! Эта библиотека развивается силами сообщества — один автор её не наполнит.

> **Прежде чем начать —** прочитайте [CLAUDE.md](./CLAUDE.md). Там все рабочие соглашения: язык, тон, структура шаблонов, идентификаторы, схема метаданных.

---

## Что можно контрибьютить

1. **Новые шаблоны политик** — заполнить недостающие позиции каталога
2. **Улучшение существующих шаблонов** — расширить, уточнить, исправить
3. **Примеры реального применения** — анонимизированные `EXAMPLES/` в папке шаблона
4. **Готовые наборы (packs)** — собрать существующие шаблоны под конкретную задачу
5. **Перевод и локализация** — если когда-нибудь захочется английскую версию
6. **Исправление опечаток и неточностей** — мелкие PR-ы тоже ценны
7. **Регуляторные маппинги** — обогащение `regulatory_refs` в metadata
8. **Граф зависимостей** — улучшение визуализаций в `docs/DEPENDENCIES.md`
9. **Автоматизация** — скрипты в `tools/`

---

## Прежде чем открывать PR

1. **Прочитайте [CLAUDE.md](./CLAUDE.md)** — рабочие соглашения
2. **Проверьте Issues** — может, ваша идея уже обсуждается
3. **Для крупных изменений — откройте Issue до PR.** Чтобы не делать большую работу зря, если предложение не примут.
4. **Один PR — одно осмысленное изменение.** Не смешивайте новый шаблон с правками в трёх других.

## Процесс: добавление нового шаблона

### Шаг 1. Откройте Issue

Используйте шаблон Issue [«New Policy»](.github/ISSUE_TEMPLATE/new-policy.md). Опишите:
- Какую проблему/обязанность покрывает политика
- В какой домен входит
- Существующие источники (стандарты, лучшие практики)
- Почему её нет в существующих шаблонах

Дождитесь обсуждения. Получите ID (формат `POL-<DOMAIN>-<NUMBER>`).

### Шаг 2. Создайте папку

```
policies/<domain>/<slug>/
├── README.md
├── TEMPLATE.md
├── GUIDE.md
├── metadata.yml
└── CHANGELOG.md
```

Используйте `policies/_TEMPLATE/` как стартовую точку — там эталонная структура.

### Шаг 3. Заполните содержимое

- **`README.md`** — описание шаблона: для кого, зачем, контекст, ограничения
- **`TEMPLATE.md`** — сам шаблон с плейсхолдерами `{{...}}` и `[ВПИСАТЬ:...]`
- **`GUIDE.md`** — как применять: процесс внедрения, частые ошибки, советы
- **`metadata.yml`** — все обязательные поля (см. [CLAUDE.md → Схема metadata.yml](./CLAUDE.md#схема-metadatayml))
- **`CHANGELOG.md`** — `1.0 — первая версия (автор: @username)`

### Шаг 4. Проверьте валидацию

```bash
python tools/validate-metadata.py policies/<domain>/<slug>/metadata.yml
```

### Шаг 5. Откройте PR

Используйте [PR-шаблон](.github/PULL_REQUEST_TEMPLATE.md). В описании:
- Ссылка на связанный Issue
- Краткое описание шаблона
- Чек-лист выполнен

### Шаг 6. Ревью

- Минимум одно ревью от мейнтейнера
- Замечания исправляются в той же ветке
- При мердже status переводится в `review`. Через 2–4 недели использования сообществом — в `active`.

## Процесс: правка существующего шаблона

1. **Мелкая правка (опечатка, уточнение):** сразу PR, ссылаться на Issue не обязательно
2. **Существенная правка (изменение смысла, добавление разделов):** через Issue
3. **Breaking change (несовместимое изменение):** обязательно через Issue + версия меняется как major (1.x → 2.0)

Обязательно обновите:
- `version` в `metadata.yml` (semver: major.minor)
- `last_reviewed` в `metadata.yml`
- `CHANGELOG.md` шаблона

---

## Семантическое версионирование шаблонов

| Изменение | Версия |
|---|---|
| Опечатка, уточнение формулировки | без изменения версии |
| Добавление раздела, расширение | minor (1.0 → 1.1) |
| Изменение смысла, удаление раздела | major (1.0 → 2.0) |
| Перевод в deprecated | без изменения версии + добавляется `superseded_by` |

## Стиль и тон

Подробно — в [CLAUDE.md](./CLAUDE.md#тон). Кратко:

- ✅ Прямо, конкретно, по делу
- ✅ Объяснять «зачем», а не только «что»
- ❌ Без канцелярита («следует отметить»)
- ❌ Без агрессивного жаргона
- ❌ Без снисходительности к читателю

---

## Тестирование шаблона

Шаблон считается готовым, если на него можно ответить «да»:

- [ ] Все шесть обязательных файлов в папке (или пять + EXAMPLES опционально)
- [ ] `metadata.yml` валиден (`tools/validate-metadata.py`)
- [ ] Все плейсхолдеры в TEMPLATE.md описаны в GUIDE.md
- [ ] Указаны как минимум 2 регуляторных маппинга (если применимо)
- [ ] Зависимости (`depends_on`) реально существуют
- [ ] Связанные политики (`related_to`) реально существуют
- [ ] CHANGELOG заполнен
- [ ] Текст вычитан, нет очевидных опечаток
- [ ] Тон соответствует [CLAUDE.md](./CLAUDE.md#тон)

## О лицензии

Все материалы библиотеки — под **CC BY-SA 4.0**. Отправляя PR, вы соглашаетесь, что ваш вклад тоже под этой лицензией.

### Что это значит для вас как контрибьютора

- Вы сохраняете авторские права на свой вклад
- Вы предоставляете остальному миру право использовать, изменять и распространять ваш вклад на условиях CC BY-SA 4.0
- Ваше имя/ник попадает в `CONTRIBUTORS.md` и в commit history

### Что это значит для пользователей шаблонов

- ✅ Можно использовать шаблоны **внутри организации**, адаптируя под себя — это не «публикация», SA не запускается
- ✅ Можно использовать в коммерческих целях
- ⚠️ Если **публикуете** свою адаптированную версию (например, на сайте, в открытом репо, в составе платного продукта для других) — должна быть под CC BY-SA 4.0
- ⚠️ Требуется указание авторства: «Источник: iMironRU IT Policies Library, CC BY-SA 4.0»

### Что является «публикацией»

| Действие | Публикация? |
|---|---|
| Внедрить адаптированный шаблон в свою компанию (внутренний документ) | Нет |
| Поделиться адаптированной версией с другой компанией в личной переписке | Нет (приватное распространение) |
| Опубликовать в открытом репо / на блоге / в книге | Да — нужна CC BY-SA |
| Включить в продукт, который продаётся клиентам | Да — нужна CC BY-SA |
| Использовать как часть консалтингового пакета для клиентов | Серая зона; зависит от того, передаётся ли документ в собственность клиента |

При сомнениях — спрашивайте в Issues.

### Не вашему вкладу

Если ваш PR содержит цитаты из проприетарных стандартов (ISO, NIST за payeall, ГОСТ) — цитируйте кратко, со ссылкой на источник, не копируя текст целиком.

## Code of Conduct

Кратко: **уважительно к людям, требовательно к работе**.

- Критика — по содержанию, не по человеку
- Конструктивные замечания, без эмоциональных оценок
- Если что-то непонятно — спросите, не предполагайте худшее
- Мейнтейнер вправе закрыть PR с пометкой «не подходит проекту» без длинных оправданий — это норма

Серьёзные нарушения (травля, дискриминация, спам) — основание для блокировки.

## Контакт

- Issues — основной канал
- Pull Requests — для конкретных изменений
- Email мейнтейнера — в профиле GitHub
