# Маркеры применимости и слои зрелости

Каждый шаблон в библиотеке имеет маркер, помогающий понять, нужен ли он именно вам.

## Маркеры

### ★ Core (базовый уровень)

**Нужно почти всем организациям.** От стартапа из трёх человек до крупной корпорации.

- В metadata: `maturity: core`
- Примеры: Политика ИБ, Политика паролей, AUP, Резервное копирование, Реагирование на инциденты, Управление изменениями

Если у вас нет политики с маркером ★ — это серьёзный пробел. Аудитор любого вменяемого стандарта спросит про неё в первую очередь.

### ◆ Standard (средний уровень)

**Нужно среднему и крупному бизнесу.** Применимо, когда:

- Сотрудников больше 30–50
- Есть IT-отдел (даже из 2–3 человек)
- Работаете с клиентскими данными
- Есть какая-то регуляторика (152-ФЗ как минимум)

- В metadata: `maturity: standard`
- Примеры: Управление мощностями, OLA, DLP, Threat Intelligence (базовый), SaaS Governance

Можно отложить на потом, если вы стартап в первый год. Но не позже, чем масштаб начинает причинять проблемы.

### ▲ Advanced (продвинутый уровень)

**Нужно зрелым или регулируемым организациям.** Применимо, когда:

- Серьёзная регуляторика (PCI DSS, СТО БР, ИСО-сертификация)
- Высокая критичность данных или сервисов
- Зрелая ИБ-команда (есть SOC, есть выделенные роли)
- Публичные продукты, ответственность перед клиентами

- В metadata: `maturity: advanced`
- Примеры: Detection engineering, Purple teaming, Chaos Engineering, Post-Quantum Cryptography, Data Lineage, AI Red Teaming

Может быть избыточно для небольшой компании. Но если ваш контекст требует — это уже не «по желанию».

### ⓘ Conditional (условно применимо)

**Только если применимо к вашему контексту.** Маркер ортогонален предыдущим — может быть на любом уровне зрелости.

- В metadata: `conditional: true`
- Примеры:
  - OT/ICS Security — только если есть производство
  - PSIRT — только если есть собственный продукт у клиентов
  - КИИ-документы — только для субъектов КИИ
  - ABC/FCPA — для крупных международных компаний

В поле `applicability_notes` указано, когда применимо.

## Как пользоваться

### Если вы оцениваете свою организацию

Пройдитесь по списку всех ★. Каждое отсутствие — пробел, который нужно либо закрыть, либо обосновать (и поместить обоснование в реестр исключений).

Затем ◆ — если применимо по размеру/контексту.

Затем ▲ — если применимо по зрелости.

Маркер ⓘ — отдельно, по контексту.

### Если вы выбираете шаблон

В каждом README шаблона указано «Кому нужна». Маркер — быстрая ориентация, README — конкретика.

### Если вы фильтруете каталог

В будущем (когда добавим автоматизацию) — фильтры по metadata.maturity и metadata.conditional дадут срез под ваш профиль.

## Тестовые вопросы для применимости

Не уверены, нужна ли политика? Проверьте по трём критериям:

1. **Закрывает реальный риск/обязанность?** Если «риск» абстрактный («ну вдруг») — отложите.
2. **Есть кто-то, кто реально будет её исполнять и контролировать?** Если нет ответственного — не пишите, это будет мёртвая бумага.
3. **Соразмерна затратам на внедрение и поддержку?** Если внедрение занимает 3 месяца, а риск минимален — может быть, не сейчас.

Три «да» — внедряйте. Хотя бы одно «нет» — отложите или замените упрощённой версией.

## Не путать маркеры с приоритетом внедрения

Маркер ★ ≠ «первым делом». Внутри Core тоже есть порядок:

1. Сначала **метаполитики** (POL-MTA-001, POL-GOV-001, POL-MTA-002)
2. Потом **доступ** (пароли, MFA, управление доступом, jml)
3. Потом **данные** (защита, бэкап)
4. Потом **операции** (изменения, инциденты, мониторинг)
5. Потом **остальное**

См. [ROADMAP.md](./ROADMAP.md) для детального порядка.
