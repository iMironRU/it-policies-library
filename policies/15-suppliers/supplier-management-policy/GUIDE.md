# Руководство по применению POL-SUP-001

## Шаг 1. Определите «критичного подрядчика»

Заполните `{{ПОРОГ_КРИТИЧНОСТИ}}` — это пороговый признак, при наличии которого подрядчику назначается статус «критичного» и к нему применяются усиленные требования.

Примеры порогов:
- Доступ к данным с грифом «Конфиденциально» и выше
- Обработка персональных данных более 500 субъектов
- Доступ к производственной инфраструктуре или облачной среде
- Оборот по договору превышает [ВПИСАТЬ: сумму в рублях]

Не обязательно применять один критерий — можно использовать несколько. Главное, чтобы критерий был ясен закупочной роли и позволял принять решение без обращения к ИБ в каждом случае.

## Шаг 2. Определите стандартные договорные оговорки

Совместно с юристом выработайте 2–3 стандартных варианта приложения к договору (или отдельного NDA) для разных уровней подрядчиков:

- **Базовое приложение** — для подрядчиков с ограниченным доступом
- **Расширенное приложение** — для критичных подрядчиков
- **DPA** — для подрядчиков, обрабатывающих ПДн

Без стандартных формулировок юристу придётся согласовывать каждый договор заново — процесс затормозится.

## Шаг 3. Создайте реестр подрядчиков

Реестр — основа контроля. Минимальная структура:

| Поле | Описание |
|---|---|
| Наименование подрядчика | |
| Куратор от Организации | |
| Дата начала / окончания договора | |
| Статус (активный / завершён) | |
| Уровень доступа (базовый / критичный) | |
| Учётные записи | |
| Дата последней проверки | |
| DPA (да/нет) | |

Хранить реестр можно в таблице, внутренней wiki или системе управления договорами. Главное — актуальность: устаревший реестр хуже его отсутствия.

## Шаг 4. Настройте ежеквартальную сверку

Ежеквартальная сверка учётных записей с реестром активных договоров — самая недооценённая практика. Типичная ситуация: договор давно закончился, а учётная запись всё ещё активна. Настройте напоминание в календаре или задачу в трекере.

## Упрощения для малых организаций

Если у вас до 10 активных подрядчиков:

- Оценку безопасности допускается проводить в формате опросного листа на 1 страницу вместо полноценного анкетирования
- Плановые проверки критичных подрядчиков можно совмещать с ежегодным пересмотром договоров
- Реестр подрядчиков может быть частью общего реестра договоров

## Типичные ошибки

**Общие учётные записи для подрядчиков.** «Все разработчики нашего подрядчика сидят под одним логином» — невозможно атрибутировать действия, невозможно отозвать доступ у конкретного человека.

**Поздний отзыв доступа.** IT-служба узнаёт об окончании договора через неделю после факта. Нужно сделать куратора явно ответственным за уведомление.

**NDA без зубов.** Обязательство конфиденциальности есть, а санкций нет. Включайте в договор явный размер неустойки или условие о взыскании убытков.

**Нет требований к субподрядчикам.** Подрядчик привлёк третью сторону, которую вы не проверяли, — данные ушли туда. Всегда требуйте согласования субподрядчиков.

**Пропуск DPA.** Если подрядчик обрабатывает ПДн, DPA — не опция, а требование ФЗ-152 ст. 6 ч. 3. Без него Организация несёт полную ответственность за нарушения при обработке.

## Раздел про уведомление об инцидентах

24 часа (базовый) и 4 часа (критичный) — это внутренние сроки уведомления Организации, не связанные с регуляторными сроками уведомления РКН. Если инцидент у подрядчика затронул ПДн субъектов, Организация самостоятельно уведомляет РКН в сроки по ФЗ-152 ст. 21 ч. 3.1: первичное — в течение 24 часов, подтверждающее — в течение 72 часов.
