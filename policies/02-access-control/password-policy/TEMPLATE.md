## 1. Назначение

Настоящая Политика устанавливает требования к паролям, используемым для аутентификации пользователей в информационных системах {{НАЗВАНИЕ_ОРГАНИЗАЦИИ}} (далее — Организация), а также правила обращения с паролями, направленные на снижение риска несанкционированного доступа.

Политика подчинена {{ССЫЛКА_НА_ПОЛИТИКУ_ИБ}}.

## 2. Область применения

Действие Политики распространяется на:

- Всех пользователей информационных систем Организации (сотрудников, подрядчиков, временных работников)
- Все информационные системы Организации, использующие парольную аутентификацию
- Личные устройства пользователей в части доступа к корпоративным ресурсам

Особые случаи:

- Для систем, в которых параметры паролей навязаны внешними требованиями (государственные информационные системы, банковские системы, специализированное ПО), применяются параметры, установленные владельцем соответствующей системы. Список таких систем ведётся {{ВЛАДЕЛЕЦ}} в [ВПИСАТЬ: ссылка на реестр исключений].

## 3. Термины и определения

| Термин | Определение |
|---|---|
| Пароль | Секретная последовательность символов, используемая для аутентификации |
| Привилегированная учётная запись | Учётная запись с правами администратора систем, доступом к критичным данным или иными расширенными правами |
| Компрометация пароля | Любое событие, при котором пароль стал или мог стать известен неуполномоченному лицу |
| Менеджер паролей | Программное обеспечение для безопасного хранения и автоматического ввода паролей |
| Парольная фраза | Длинный пароль, состоящий из нескольких слов |

## 4. Требования к паролям

### 4.1. Требования к длине и составу

Для **пользовательских учётных записей**:

- Минимальная длина: **12 символов**
- Состав: разрешены любые символы, включая пробелы и Unicode
- Не допускается использование пароля, входящего в список наиболее распространённых утечённых паролей (проверка при установке)
- Не допускается использование пароля, содержащего имя пользователя, логин, ФИО или название Организации

Для **привилегированных учётных записей**:

- Минимальная длина: **16 символов**
- Все остальные требования из п. 4.1 применяются дополнительно
- Рекомендуется использование автоматически генерируемых паролей высокой энтропии или ключей вместо паролей

### 4.2. Срок действия пароля

- **Плановая смена пароля по календарному принципу не требуется** (соответствует современным рекомендациям NIST SP 800-63B)
- Принудительная смена пароля производится в следующих случаях:
  - Известная или подозреваемая компрометация
  - Утечка базы данных аутентификации
  - При смене сотрудника, имеющего доступ к данному паролю (например, общие учётки — но общих учёток быть не должно, см. п. 4.4)
  - При первичной выдаче (временный пароль меняется при первом входе)
- Для систем, в которых смена пароля по календарю навязана требованиями владельца системы (ГИС, банк-клиент), применяется устанавливаемая ими периодичность

### 4.3. История паролей

При смене пароля система не должна позволять установить любой из последних **10** паролей данного пользователя.

### 4.4. Запрет на совместное использование

- Каждый пользователь имеет персональную учётную запись
- Использование одной учётной записи несколькими лицами запрещено
- Передача пароля другому лицу запрещена, в том числе руководителю, коллеге, сотруднику службы поддержки

Исключения возможны только в чрезвычайных ситуациях (отсутствие сотрудника, имеющего доступ к критичной системе, при производственной необходимости) — порядок установлен в [ВПИСАТЬ: ссылка на регламент экстренного доступа].

### 4.5. Защита паролей от компрометации

Пользователь обязан:

- Не записывать пароли в местах, доступных для других лиц (включая стикеры на мониторе, документы в общих папках)
- Не передавать пароль по незащищённым каналам связи (мессенджеры, SMS, email)
- Не использовать корпоративный пароль для личных сервисов и наоборот
- Не вводить пароль в недоверенных средах (чужой компьютер, общественные терминалы)
- Использовать корпоративный менеджер паролей (при его наличии) для хранения

Допускается:

- Использование менеджеров паролей (корпоративных и личных) для хранения и автоматического ввода паролей
- Физическое хранение пароля в запертом сейфе/шкафу (для критичных аварийных паролей)

### 4.6. Особые требования для привилегированных учётных записей

- Хранение паролей привилегированных учёток — только в корпоративном vault-решении (см. {{ССЫЛКА_НА_ПОЛИТИКУ_СЕКРЕТОВ}})
- Использование паролей через систему привилегированного доступа (PAM/PSM), где это технически возможно
- Запись сессий для критичных систем

## 5. Многофакторная аутентификация

Многофакторная аутентификация (MFA) является обязательной для определённых категорий доступа в соответствии с {{ССЫЛКА_НА_ПОЛИТИКУ_MFA}}. Настоящая Политика не отменяет требования MFA, а дополняет их в части первого фактора (пароля).

## 6. Действия при компрометации

При обнаружении компрометации пароля или подозрении на неё пользователь обязан:

1. Немедленно сменить пароль самостоятельно (если есть техническая возможность)
2. Уведомить о факте компрометации службу поддержки по адресу {{КАНАЛ_СООБЩЕНИЯ_ОБ_ИНЦИДЕНТАХ}}
3. Указать в уведомлении:
   - Какая учётная запись была скомпрометирована
   - Обстоятельства компрометации (по возможности)
   - Время обнаружения

При компрометации **привилегированной учётной записи** дополнительно:

4. Уведомление направляется в течение **30 минут** с момента обнаружения
5. Учётная запись немедленно блокируется (производится {{ВЛАДЕЛЕЦ}} или дежурным администратором)
6. Производится расследование инцидента в порядке, установленном {{ССЫЛКА_НА_ПОЛИТИКУ_РЕАГИРОВАНИЯ_НА_ИНЦИДЕНТЫ}}

## 7. Технические меры

Технические администраторы информационных систем обязаны:

- Обеспечить хранение паролей в виде криптографически стойких хэшей (bcrypt, Argon2, scrypt с современными параметрами; не MD5, не SHA1, не «соль» отсутствует)
- Обеспечить передачу паролей только по защищённым каналам (HTTPS/TLS не ниже 1.2)
- Реализовать блокировку учётной записи после {{ЧИСЛО_ПОПЫТОК}} неуспешных попыток ввода пароля
- Обеспечить логирование событий аутентификации (успешных и неуспешных)
- Не отображать пароль на экране при вводе и не сохранять в логах в открытом виде
- Реализовать механизм безопасного восстановления пароля без раскрытия текущего значения

## 8. Контроль соблюдения

Контроль соблюдения Политики осуществляется:

- Техническими средствами — системы аутентификации настроены на принудительное выполнение требований Политики
- Аудитом — плановая проверка не реже одного раза в 12 месяцев
- В рамках расследований инцидентов ИБ

## 9. Ответственность за нарушения

Нарушение требований настоящей Политики, повлёкшее или способное повлечь компрометацию информационных активов Организации, влечёт ответственность в соответствии с {{ССЫЛКА_НА_ПОЛИТИКУ_ИБ}} и трудовым законодательством Российской Федерации.
