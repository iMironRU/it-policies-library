# Руководство по применению POL-IAM-003

## Кому читать этот файл

IT-администратору или ответственному за ИБ, который внедряет управление доступом с нуля или формализует существующую практику.

---

## Шаг 1 — Создайте ролевую матрицу

Это самый важный артефакт, без которого политика не работает. Матрица отвечает на вопрос: «Кто с какой должностью получает доступ к каким системам?»

**Минимальная структура:**

| Роль / Должность | Система 1 (CRM) | Система 2 (1С) | Система 3 (GitHub) | Облако (AWS/Yandex) |
|---|---|---|---|---|
| Разработчик | Нет | Нет | Чтение + запись | Dev-среда |
| Менеджер по продажам | Полный доступ | Просмотр | Нет | Нет |
| Бухгалтер | Нет | Полный | Нет | Нет |
| Системный администратор | Администратор | Администратор | Владелец | Полный |

Матрица хранится в {{СИСТЕМА_ЗАДАЧ}} или общем документе с ограниченным доступом. Обновляется при добавлении новых систем или ролей.

## Шаг 2 — Настройте процесс onboarding/offboarding

**Самая критичная часть политики — offboarding.** Устаревшие учётные записи уволенных сотрудников — один из самых распространённых векторов атак.

Проверьте сейчас: запросите у HR список уволенных за последний год и сверьте с активными учётными записями в {{СИСТЕМА_IDM}}. Скорее всего, найдёте «призраки».

**Рекомендуемая процедура offboarding:**

```
День X-1 (последний рабочий день минус 1):
  → HR уведомляет IT о дате ухода
  → IT готовит список учётных записей к блокировке

День X (последний рабочий день):
  → 17:00 — блокировка всех учётных записей
  → Отзыв токенов, API-ключей, SSH-ключей
  → Перевод сервисных учётных записей на другого владельца

День X+30:
  → Финальное удаление учётных записей (после проверки, что ничего не сломалось)
```

## Шаг 3 — Определите, нужна ли PAM-система

PAM (Privileged Access Management) — специализированный инструмент для управления привилегированным доступом: запись сессий, временная выдача прав, just-in-time access.

**Нужна PAM-система если:**
- Более 5 администраторов с привилегированным доступом
- Есть требования аудита (ISO 27001, SOC 2, банковские требования)
- Регулярный доступ внешних подрядчиков к продакшену

**Достаточно процедуры без PAM:**
- Небольшая команда (2–5 технических сотрудников)
- Привилегированный доступ нужен редко и только своим

**Варианты PAM:**

| Инструмент | Тип | Особенности |
|---|---|---|
| HashiCorp Vault | Self-hosted | Just-in-time access, секреты |
| Teleport | Self-hosted / Cloud | SSH/Kubernetes access, запись сессий |
| CyberArk | Enterprise | Полнофункциональный, дорогой |
| Boundary (HashiCorp) | Self-hosted | Брокер доступа к инфраструктуре |

## Шаг 4 — Настройте MFA

§8 определяет, где MFA обязательна. Порядок внедрения по приоритету:

1. **VPN и удалённый доступ** — максимальный риск, включить первым
2. **Корпоративная почта и Google/Microsoft workspace** — самый частый вектор фишинга
3. **Репозитории кода** — GitHub/GitLab поддерживают TOTP и FIDO2 нативно
4. **Облачные консоли** (AWS, Yandex Cloud) — обязательно, там деньги и данные
5. **Системы с ПДн** — требование ФЗ-152/ФСТЭК

**О SMS-кодах:** §8 допускает SMS как «вынужденный минимум». Это значит: если ничего другого нет — лучше SMS, чем ничего. Но SMS-коды уязвимы к SIM-swapping и перехвату SS7. При первой возможности переводите на TOTP или FIDO2.

## Шаг 5 — Автоматизируйте ревью доступа

Ревью вручную раз в 6 месяцев — это 100 писем руководителям «подтвердите права своих подчинённых» и 30% ответов. Упростите:

1. Выгрузите из {{СИСТЕМА_IDM}} список пользователей и их прав
2. Разошлите каждому руководителю только его подчинённых (не весь список)
3. Попросите ответить: «Подтверждаю» / «Отозвать для: [список]»
4. Зафиксируйте результаты и выполните отзыв

Для организаций, использующих Entra ID (Azure AD) или Google Workspace, есть встроенные функции Access Reviews.

## Частые ошибки

### Ошибка 1: Не отзывать права при смене роли, только добавлять
Сотрудник, перешедший из разработки в менеджмент, часто сохраняет все старые права разработчика плюс получает новые. Через год у него доступ ко всему. Смена роли = отзыв старых прав + выдача новых.

### Ошибка 2: Общая учётная запись «admin»
Если пять человек знают пароль от admin — неизвестно, кто и что сделал при расследовании инцидента. Каждый получает именную учётную запись с нужным уровнем прав.

### Ошибка 3: Разработчики с постоянным продакшен-доступом
«Удобно для дебага» создаёт постоянный вектор атаки. Используйте just-in-time access: временный доступ выдаётся под конкретную задачу и автоматически истекает.

### Ошибка 4: Сервисные учётные записи без владельца
«Это аккаунт Васи, он уволился» — и никто не знает пароль, а сервис работает. У каждой сервисной учётной записи должен быть текущий владелец.
