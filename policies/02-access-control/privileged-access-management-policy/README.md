# POL-IAM-002 — Политика управления привилегированным доступом

**Maturity:** ◆ Standard  
**Владелец:** CISO  
**Статус:** draft

---

## Зачем нужна эта политика

Привилегированный доступ — наиболее опасный вектор атаки и злоупотребления в IT-инфраструктуре. Статистика подтверждает: подавляющее большинство резонансных утечек данных и успешных атак на компании связаны с компрометацией учётных записей с административными правами — неважно, внешней атакой или действиями инсайдера.

Типичные проблемы без PAM-политики:

- **Общие учётные записи**: несколько администраторов работают под одним `admin`. После инцидента невозможно установить, кто и что делал.
- **Постоянные привилегии**: учётная запись Domain Admin используется для ежедневной работы — проверки почты, браузинга. Одна фишинговая ссылка — и злоумышленник получает ключи от королевства.
- **Неконтролируемый доступ подрядчиков**: внешний специалист подключается по RDP с полными правами без записи сессии и без отзыва доступа после завершения работ.
- **Секреты в коде**: пароль сервисной учётной записи вшит в `config.yaml` и лежит в GitLab с 2019 года.
- **Нет ревизии**: учётная запись уволенного сотрудника с правами DBA продолжает существовать.

Эта политика вводит управляемый периметр: PAM-система, JIT-доступ, обязательная запись сессий, ревизия и аварийный механизм на случай, когда всё сломалось.

---

## Область применения

- Все сотрудники с административными правами (системные администраторы, сетевые инженеры, DBA, DevOps/SRE)
- Разработчики с доступом к производственным средам
- Подрядчики, получающие привилегированный доступ
- Сервисные учётные записи приложений

## Ключевые решения при внедрении

1. **PAM-решение**: выбор платформы (CyberArk, Delinea Secret Server, BeyondTrust, HashiCorp Vault + Boundary, самостоятельная реализация на основе бесплатных инструментов). Для небольших организаций возможен старт с HashiCorp Vault для хранения секретов + jump-сервер с sudo-логированием.
2. **JIT vs. постоянный доступ**: в идеале — весь привилегированный доступ через JIT. На практике первый этап — хотя бы раздельные учётные записи и jump-сервер.
3. **Запись сессий**: сколько хранить, куда направлять, кто просматривает — технический вопрос с юридическими последствиями (трудовой кодекс и уведомление сотрудников).
4. **Break-glass**: без него политика заблокирует работу при сбое PAM. Нужна описанная и протестированная процедура.
