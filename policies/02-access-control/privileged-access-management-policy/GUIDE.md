# GUIDE — POL-IAM-002 Политика управления привилегированным доступом

Руководство по внедрению: что приоритизировать, как реализовать ключевые требования и где чаще всего ошибаются.

---

## С чего начать: приоритеты внедрения

PAM — не проект одного дня. Реалистичная дорожная карта:

### Этап 1 (быстрые победы, 1–4 недели)
- Инвентаризация привилегированных учётных записей: составьте полный список (AD groups, локальные admin, сервисные учётные записи, cloud root).
- Создайте именные учётные записи для каждого администратора, если используются общие.
- Включите МФА для всех привилегированных учётных записей.
- Заблокируйте cloud root: создайте IAM-роли для администраторов, отзовите постоянный доступ у root.
- Задокументируйте процедуру break-glass и создайте физически защищённые учётные данные.

### Этап 2 (архитектурные изменения, 1–3 месяца)
- Разверните jump-сервер. Настройте сетевую сегментацию так, чтобы SSH/RDP в инфраструктуру шёл только через него.
- Запустите централизованное хранилище паролей (HashiCorp Vault, CyberArk, Delinea).
- Перенесите секреты сервисных учётных записей из кода и конфигов в vault.
- Настройте ротацию паролей привилегированных учётных записей.

### Этап 3 (зрелый PAM, 3–12 месяцев)
- Внедрите JIT-доступ: права выдаются по запросу, автоматически отзываются.
- Настройте запись сессий через jump-сервер.
- Интегрируйте PAM с SIEM для алертинга.
- Первая ревизия привилегированных учётных записей по новой процедуре.

## Jump-сервер: минимальная реализация

Если полноценный PAM пока недоступен, jump-сервер — первая линия контроля.

**Минимальный стек для Linux-инфраструктуры:**
- Отдельная ВМ в management VLAN, доступная только из корпоративной сети или VPN.
- OpenSSH с ForceCommand + ограниченный список пользователей (AllowUsers).
- `sudo` с включённым логированием всех команд: `Defaults logfile=/var/log/sudo.log`.
- `script` или `ttyrec` для базовой записи сессии. Для production — PAM-модуль с направлением записи в защищённое хранилище.
- `auditd` для аудита системных вызовов.

**Минимальный стек для Windows-инфраструктуры:**
- Выделенный PAW (Privileged Access Workstation) или jump-сервер на Windows Server.
- RDP Gateway с вынесенными логами.
- Windows Event Forwarding → centralized log.
- LAPS (Local Administrator Password Solution) для управления паролями локальных администраторов на рабочих станциях.

## Сервисные учётные записи: типичные ошибки

### Ошибка 1: секрет в коде
```yaml
# ПЛОХО — не делайте так
database:
  password: "P@ssw0rd123"
```
```yaml
# ХОРОШО — ссылка на vault
database:
  password_ref: "vault:secret/prod/db/password"
```

**Как найти уже существующие секреты в репозиториях:**
- `git log --all -p | grep -i 'password\|secret\|api_key\|token'`
- Инструменты: GitLeaks, TruffleHog, Semgrep (правило secrets).

### Ошибка 2: избыточные права сервисной учётной записи
Приложение, которому нужно только читать из одной таблицы, работает под `sa` (system administrator SQL Server) или Domain Admin. Поиск: отфильтруйте сервисные учётные записи в AD по членству в привилегированных группах.

### Ошибка 3: сервисная учётная запись без владельца
При увольнении разработчика, создавшего учётную запись, никто не знает, что с ней делать. Требуйте указывать владельца при создании — это поле в AD / ServiceNow.

### Ошибка 4: интерактивный вход под сервисной учётной записью
В Windows: Group Policy → Computer Configuration → Windows Settings → Security Settings → Local Policies → User Rights Assignment → "Deny log on locally" для всех сервисных учётных записей. В Linux: `nologin` shell (`usermod -s /sbin/nologin svc_account`).

## Ревизия привилегированных учётных записей: процедура

### Подготовка (за неделю до ревизии)
1. Выгрузить из AD все группы с привилегированными правами и их членов.
2. Выгрузить список локальных администраторов со всех серверов (скрипт или SIEM).
3. Выгрузить сервисные учётные записи с датой последнего использования.
4. Разослать руководителям список учётных записей их сотрудников для подтверждения.

### Проведение ревизии
Для каждой привилегированной учётной записи:
- [ ] Принадлежит действующему сотруднику / активному сервису?
- [ ] Руководитель/владелец подтвердил необходимость прав?
- [ ] Объём прав соответствует текущей роли (нет "археологических" прав)?
- [ ] Дата последнего использования — в разумных пределах (не использовалась > 90 дней → подозрение)?

### Действия по итогам
- Неподтверждённые учётные записи: блокировка немедленно, удаление через 30 дней (после удостоверения в отсутствии зависимостей).
- Избыточные права: отзыв прав с уведомлением руководителя.
- Неактивные сервисные учётные записи: анализ зависимостей → блокировка → удаление.

## Break-glass: как организовать правильно

Процедура аварийного доступа провальна, если её не тестировать. Типичные проблемы:

**«Конверт в сейфе, а сейф у системного администратора»** — это не break-glass, это зависимость от одного человека.

Рекомендуемая схема:
1. Аварийные учётные данные хранятся в двух физически разделённых местах (например, сейф CISO и сейф генерального директора).
2. Доступ к обоим требует одновременного участия двух уполномоченных лиц (двойной контроль).
3. Каждое вскрытие конверта фиксируется: кто, когда, по какой причине.
4. После использования аварийного доступа — немедленная смена пароля и оформление нового конверта.
5. Проверка работоспособности break-glass — раз в год без реального вскрытия (убедиться, что учётные данные актуальны и не заблокированы).

## Мониторинг: что алертить

| Событие | Приоритет | Действие |
|---|---|---|
| Успешный вход под Domain Admin / root в нерабочее время | Высокий | Немедленное расследование |
| Многократные неуспешные попытки входа в привилегированные учётные записи | Высокий | Блокировка + расследование |
| Использование аварийного доступа (break-glass) | Высокий | Уведомление CISO + документирование |
| Попытка отключить аудит или журналирование | Критичный | Немедленный алерт + блокировка |
| Привилегированная учётная запись вне jump-сервера | Высокий | Проверка и блокировка |
| Добавление нового члена в привилегированную группу AD | Средний | Проверка наличия согласованной заявки |
| Неуспешная МФА для привилегированной учётной записи | Средний | Мониторинг паттерна |
| Доступ к cloud root вне процедуры break-glass | Критичный | Немедленное расследование |

## Выбор PAM-решения: краткий обзор

| Решение | Тип | Подходит для |
|---|---|---|
| CyberArk PAM | Коммерческий | Крупные организации, высокий уровень зрелости |
| Delinea Secret Server | Коммерческий | Средние и крупные организации |
| BeyondTrust Password Safe | Коммерческий | Средние организации |
| HashiCorp Vault + Boundary | Open source / Enterprise | Технические команды, DevOps-ориентированные организации |
| Teleport | Open source / Enterprise | Облачные и гибридные среды, SSH/k8s |
| Wallix Bastion | Коммерческий, есть РФ-версия | Организации с требованиями к локализации |

Для небольших организаций с ограниченным бюджетом: HashiCorp Vault (secrets) + Teleport или self-hosted jump-сервер с sudo-логированием — вполне рабочая комбинация.
