## 1. Назначение

Настоящая политика устанавливает требования к управлению привилегированным доступом в {{НАЗВАНИЕ_ОРГАНИЗАЦИИ}}: идентификации привилегированных учётных записей, их выдаче, контролю, мониторингу и отзыву.

Привилегированный доступ — наиболее высокорисковый элемент системы управления доступом. Компрометация административной учётной записи даёт злоумышленнику полный контроль над системой и возможность уничтожить следы проникновения. Инциденты, связанные с злоупотреблением привилегированным доступом, занимают первые строчки в статистике крупных утечек данных — как внешних атак, так и действий инсайдеров.

Политика дополняет {{ССЫЛКА_НА_ПОЛИТИКУ_ДОСТУПА}} применительно к учётным записям с расширенными правами.

## 2. Область применения

Политика распространяется на:

- всех сотрудников и подрядчиков, имеющих или запрашивающих привилегированный доступ к системам {{НАЗВАНИЕ_ОРГАНИЗАЦИИ}};
- все системы, содержащие конфиденциальные данные или критичные для деятельности организации: серверная инфраструктура, сетевое оборудование, базы данных, облачные среды, средства защиты информации, системы резервного копирования;
- разработчиков, имеющих права доступа к производственным (production) средам.

## 3. Термины и сокращения

| Термин | Определение |
|---|---|
| Привилегированная учётная запись | Учётная запись с правами, превышающими обычные пользовательские: локальный администратор, доменный администратор, root, DBA, учётные записи операционных систем и сетевых устройств с полными правами |
| PAM | Privileged Access Management — система управления привилегированным доступом |
| Jump-сервер (bastion host) | Выделенный сервер-посредник, через который осуществляется весь привилегированный доступ к защищённым системам |
| Хранилище паролей (Password Vault) | Защищённое централизованное хранилище учётных данных привилегированных и сервисных учётных записей |
| Just-in-Time (JIT) доступ | Предоставление привилегированного доступа только на время выполнения задачи с автоматическим отзывом по истечении срока |
| Сервисная учётная запись | Учётная запись, используемая приложением или сервисом (не человеком) для взаимодействия с другими системами |
| Аварийный доступ (break-glass) | Механизм экстренного получения привилегированного доступа в критических ситуациях, когда стандартные процедуры недоступны |
| Запись сессии | Полная фиксация действий в ходе привилегированной сессии: командная строка, нажатия клавиш, экранная активность |
| Разделение обязанностей (SoD) | Разграничение полномочий, при котором ни один человек не имеет единоличного контроля над критичными операциями |

## 4. Управление привилегированными учётными записями

### 4.1. Типы привилегированных учётных записей

{{НАЗВАНИЕ_ОРГАНИЗАЦИИ}} выделяет следующие категории привилегированных учётных записей:

| Тип | Примеры | Требования |
|---|---|---|
| Доменные / системные администраторы | Domain Admin, Enterprise Admin, root | Только в PAM; JIT обязателен |
| Локальные администраторы | Локальный admin на рабочих станциях и серверах | Управляемые через LAPS или PAM |
| Сетевые администраторы | Учётные записи управления маршрутизаторами, коммутаторами, МЭ | Только через jump-сервер |
| Администраторы СУБД | DBA, sa, sys, oracle | Только в PAM; ротация паролей |
| Cloud root / owner | AWS root, Azure Global Administrator | Ротация после каждого использования; без постоянного доступа; JIT только при необходимости |
| Сервисные учётные записи | Технические учётные записи приложений | Управляемые пароли; минимальные привилегии |
| Аварийный доступ (break-glass) | Аварийный администратор домена | Опечатанные учётные данные; аудит использования |

### 4.2. Принципы выдачи привилегированного доступа

- **Минимальные привилегии**: привилегированный доступ предоставляется только в объёме, необходимом для выполнения конкретной задачи.
- **Just-in-Time**: постоянное наличие привилегированных прав не допускается там, где технически реализован JIT. Права выдаются на запрос и автоматически отзываются по истечении {{СРОК_СЕССИИ_ПРИВИЛЕГИИ}}.
- **Раздельные учётные записи**: сотрудник, нуждающийся в привилегированном доступе, использует отдельную учётную запись (не совпадающую с ежедневной рабочей). Привилегированная учётная запись не используется для просмотра почты, браузинга и работы с документами.
- **Запрет разделяемых учётных записей**: каждый сотрудник работает под персональной привилегированной учётной записью. Общие учётные записи для повседневной работы запрещены. Встроенные системные учётные записи (`administrator`, `root`, `sa`) блокируются или переименовываются там, где это позволяет система; если они необходимы как аварийный механизм, их учётные данные хранятся по процедуре §4.6 и используются только в рамках неё.
- **Разделение обязанностей**: операции с высоким риском (массовое удаление данных, изменение конфигурации RBAC, отключение средств защиты) требуют участия двух уполномоченных сотрудников или прохождения второго уровня утверждения в PAM.

### 4.3. Запрос и утверждение

Привилегированный доступ предоставляется по заявке, согласованной с непосредственным руководителем и {{ОТВЕТСТВЕННЫЙ_ЗА_ИБ}}. Заявка содержит:
- системы и уровень доступа;
- обоснование (для выполнения какой задачи или в рамках какой роли);
- ожидаемый срок действия.

### 4.4. Ревизия привилегированных учётных записей

{{ОТВЕТСТВЕННЫЙ_ЗА_ИБ}} проводит ревизию всех привилегированных учётных записей не реже {{СРОК_РЕВИЗИИ_ПРИВИЛЕГИЙ}}. Ревизия включает:
- подтверждение актуальности и обоснованности прав каждой учётной записи у владельца бизнес-процесса;
- отзыв прав, не подтверждённых владельцем;
- выявление неиспользуемых и устаревших учётных записей.

При увольнении или переводе сотрудника привилегированный доступ отзывается в течение рабочего дня — независимо от плановых циклов ревизии.

### 4.5. Управление паролями привилегированных учётных записей

Пароли привилегированных учётных записей хранятся в {{PAM_РЕШЕНИЕ}} или аналогичном защищённом хранилище. Дополнительно к требованиям {{ССЫЛКА_НА_ПОЛИТИКУ_ПАРОЛЕЙ}}:

- пароли привилегированных учётных записей ротируются автоматически после каждого использования или не реже чем раз в 90 дней;
- пароль привилегированной учётной записи не известен пользователю напрямую, если PAM-система обеспечивает выдачу сессии без раскрытия пароля;
- пароли сервисных учётных записей ротируются не реже {{СРОК_РОТАЦИИ_ПАРОЛЕЙ_СЕРВИСНЫХ}}.

### 4.6. Аварийный доступ (break-glass)

Аварийный доступ используется только при недоступности штатных механизмов привилегированного доступа (сбой PAM, аварийное восстановление инфраструктуры).

- Учётные данные аварийного доступа хранятся в физически защищённом месте (например, опечатанный конверт в сейфе).
- Факт использования аварийного доступа немедленно фиксируется и уведомляется {{ОТВЕТСТВЕННЫЙ_ЗА_ИБ}}.
- Не позднее {{СРОК_ОФОРМЛЕНИЯ_АВАРИЙНОГО}} после использования оформляется документация с обоснованием и перечнем выполненных действий.
- После использования пароль аварийного доступа немедленно меняется.

## 5. Технические требования к привилегированному доступу

### 5.1. Jump-сервер и изоляция

Весь привилегированный доступ к серверам, сетевому оборудованию и базам данных осуществляется через {{JUMP_СЕРВЕР}}. Прямые SSH/RDP-соединения в обход jump-сервера запрещены.

Jump-сервер:
- находится в отдельном сетевом сегменте (management VLAN/сеть управления);
- недоступен из публичных сетей напрямую;
- имеет усиленную конфигурацию (hardening по CIS Benchmarks или ФСТЭК);
- обеспечивает полную запись сессий.

### 5.2. Многофакторная аутентификация

Многофакторная аутентификация (МФА) обязательна для всех привилегированных учётных записей без исключений. Допустимые второй фактор: аппаратный токен (FIDO2/U2F), приложение-аутентификатор (TOTP). Использование SMS-кода в качестве второго фактора для административных учётных записей не рекомендуется и допускается только при отсутствии технической возможности применить более надёжный метод.

### 5.3. Запись и мониторинг привилегированных сессий

Все привилегированные сессии записываются:
- для консольного/командного доступа: полная запись введённых команд (keystroke logging);
- для графического доступа (RDP, VDI): видеозапись экранной активности.

Записи сессий хранятся не менее {{СРОК_ХРАНЕНИЯ_ЗАПИСЕЙ}} в защищённом от изменений хранилище, недоступном для самого пользователя, чья сессия записывается.

{{ОТВЕТСТВЕННЫЙ_ЗА_ИБ}} проводит выборочный или инициированный инцидентом просмотр записей сессий. Факт записи доводится до сведения сотрудников.

### 5.4. Управление привилегированным доступом в облаке

- Root/Owner-учётные записи облачных платформ (AWS, Azure, GCP, Яндекс.Облако и аналоги) используются только для первоначальной настройки и критических операций, недоступных через IAM-роли. Для повседневных задач администрирования используются персональные IAM-учётные записи с ограниченными полномочиями.
- Cloud root credentials хранятся в {{PAM_РЕШЕНИЕ}}.
- Для привилегированных операций в облаке применяется JIT-механизм (Privileged Identity Management, AWS IAM Identity Center или аналог).
- Управление ключами API и сервисными учётными записями облачных платформ — в соответствии с {{ССЫЛКА_НА_ПОЛИТИКУ_ОБЛАКА}}.

## 6. Сервисные учётные записи

### 6.1. Требования к сервисным учётным записям

Сервисные учётные записи (технические учётные записи для приложений, сервисов и автоматизации):

- создаются с именованием, явно указывающим на назначение (например, `svc-app-name-prod`);
- имеют минимально необходимые права для выполнения функции приложения;
- не используются людьми для интерактивного входа;
- для каждой сервисной учётной записи определён ответственный владелец из числа сотрудников;
- включаются в ревизию по §4.4.

### 6.2. Секреты сервисных учётных записей

- Пароли и ключи сервисных учётных записей не хранятся в открытом виде в коде, конфигурационных файлах или скриптах. Для хранения используется {{PAM_РЕШЕНИЕ}} или secrets manager.
- Приоритет отдаётся механизмам аутентификации без хранения долгосрочных паролей: Managed Identity (Azure), IAM Roles (AWS), Workload Identity (GCP/k8s).
- Встраивание учётных данных в репозитории — нарушение политики, квалифицируемое как инцидент ИБ.

## 7. Привилегированный доступ подрядчиков и внешних лиц

Привилегированный доступ для подрядчиков и внешних специалистов предоставляется только при выполнении следующих условий (в дополнение к требованиям {{ССЫЛКА_НА_ПОЛИТИКУ_ПОДРЯДЧИКОВ}}):

- действующее соглашение о конфиденциальности (NDA) и договор с определёнными рамками доступа;
- именная учётная запись (не общая);
- МФА обязательна;
- доступ строго через jump-сервер с обязательной записью сессий;
- доступ ограничен временными рамками выполнения задачи и отзывается сразу по её завершении;
- удалённый доступ осуществляется только через утверждённые VPN-каналы.

## 8. Аудит и журналирование

- Все действия с привилегированными учётными записями журналируются: попытки аутентификации (успешные и неуспешные), создание/изменение/удаление учётных записей и прав, запуск привилегированных процессов, доступ к критичным данным.
- Журналы направляются в централизованную SIEM-систему или защищённое хранилище и недоступны для изменения пользователями, чьи действия журналируются.
- Следующие события немедленно попадают в алертинг: многократные неуспешные попытки входа под привилегированными учётными записями, вход в нерабочее время, использование аварийного доступа, попытка отключить журналирование или запись сессий.

## 9. Управление изменениями

Изменения в инфраструктуре, выполняемые с привилегированным доступом, проводятся в соответствии с {{ССЫЛКА_НА_ПОЛИТИКУ_ИЗМЕНЕНИЙ}}. Операции в производственной среде без RFC не допускаются, за исключением аварийных ситуаций — в этом случае документирование выполняется постфактум в срок, установленный {{ССЫЛКА_НА_ПОЛИТИКУ_ИЗМЕНЕНИЙ}}.

## 10. Ответственность

| Роль | Обязанности |
|---|---|
| {{ОТВЕТСТВЕННЫЙ_ЗА_ИБ}} | Утверждение запросов на привилегированный доступ; проведение ревизий; управление PAM-системой; мониторинг алертов; расследование инцидентов |
| IT-администраторы | Соблюдение настоящей политики при работе; использование только PAM для привилегированного доступа; немедленное уведомление об инцидентах |
| Руководители подразделений | Согласование заявок на привилегированный доступ для своих сотрудников; уведомление об увольнении/переводе в день принятия решения |
| Разработчики | Соблюдение требований §6 для сервисных учётных записей; запрет хранения секретов в коде |
| Подрядчики | Использование только предоставленных именных учётных записей через jump-сервер; уведомление об окончании работ |

## 11. Контроль соблюдения

- **{{СРОК_РЕВИЗИИ_ПРИВИЛЕГИЙ}}**: ревизия всех привилегированных учётных записей.
- **Ежегодно**: аудит соответствия PAM-конфигурации требованиям политики; проверка журналов на наличие аномалий; пентест сценариев получения привилегированного доступа.
- **Непрерывно**: автоматизированный алертинг по аномальному поведению привилегированных учётных записей в SIEM.
- Несанкционированное использование привилегированного доступа или попытка его получения в обход PAM квалифицируется как инцидент ИБ по процедуре {{ССЫЛКА_НА_ПОЛИТИКУ_ИНЦИДЕНТОВ}}.

## 12. Последствия несоблюдения требований

Нарушение требований настоящей политики влечёт:

- дисциплинарные меры в соответствии с трудовым законодательством РФ и внутренними нормативными документами;
- немедленный отзыв привилегированного доступа до завершения расследования;
- при установленном злоупотреблении привилегированным доступом — обращение в правоохранительные органы в соответствии со ст. 272–274.1 УК РФ (неправомерный доступ к компьютерной информации, создание/использование вредоносных программ, нарушение правил эксплуатации);
- для подрядчиков — расторжение договора.
