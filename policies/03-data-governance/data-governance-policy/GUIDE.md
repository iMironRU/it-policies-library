# GUIDE — POL-DGV-001 Политика управления данными

Руководство по внедрению: как запустить Data Governance с нуля, организовать ключевые процессы и избежать типичных ловушек.

---

## С чего начать: минимальная работающая структура

Data Governance провальна, если начать с полного описания всего. Разумная стратегия — итеративный старт:

### Этап 1 (1–2 месяца): фундамент
1. Назначьте CDO или ответственного за данные — одного человека, не комитет.
2. Определите топ-5 доменов данных (обычно: клиенты, продукты/услуги, финансы, сотрудники, договоры/контрагенты).
3. Для каждого домена назначьте владельца (руководитель, который реально принимает решения) и стюарда (человек, который работает с данными ежедневно).
4. Создайте простой реестр доменов: таблица в Confluence/Notion с 5 столбцами (домен, владелец, стюард, системы-источники, класс конфиденциальности).

### Этап 2 (3–6 месяцев): каталог и качество
5. Выберите инструмент каталога данных (см. ниже) и начните регистрировать критичные наборы данных.
6. Запустите первый цикл контроля качества для мастер-данных (клиенты, продукты): задайте метрики, измерьте, зафиксируйте базовый уровень.
7. Введите процесс: любой новый набор данных регистрируется в каталоге до ввода в эксплуатацию.

### Этап 3 (6–12 месяцев): зрелость
8. Автоматизируйте мониторинг качества (dbt tests, Great Expectations, SQL-проверки в CI).
9. Введите lineage: карта потоков данных между системами.
10. Первый ежегодный аудит: полнота метаданных, соблюдение сроков хранения, неиспользуемые наборы данных.

## Управление мастер-данными: чеклист

Мастер-данные — наиболее болезненная область: одни и те же клиенты в CRM и в биллинге с разными ID, дублирующиеся контрагенты в 1С — всё это стоит денег.

### Признаки проблемы с мастер-данными
- В разных системах один клиент имеет разные атрибуты (адрес, телефон, ИНН).
- Нет единого «золотого» источника — каждая система считает себя главной.
- Аналитики тратят >30% времени на «склейку» данных из разных источников.
- Отчёты из разных систем дают разные цифры по одной и той же метрике.

### Минимальные шаги
1. Для каждого класса мастер-данных определите MDM-систему (master) — единственную authoritative source.
2. Запретите вносить изменения в мастер-атрибуты вне MDM-системы (в т.ч. через прямые UPDATE в БД).
3. Задокументируйте механизм синхронизации: кто, когда, как реплицирует данные из MDM в потребляющие системы.
4. Введите golden record: процедуру разрешения конфликтов при дублировании.

## Качество данных: метрики и инструменты

### Базовые SQL-проверки качества

```sql
-- Полнота: процент заполненных обязательных полей
SELECT
  COUNT(*) AS total,
  COUNT(email) AS filled_email,
  ROUND(COUNT(email) * 100.0 / COUNT(*), 1) AS completeness_pct
FROM customers
WHERE created_at >= CURRENT_DATE - INTERVAL '30 days';

-- Уникальность: дубликаты по ИНН
SELECT inn, COUNT(*) AS cnt
FROM contractors
GROUP BY inn
HAVING COUNT(*) > 1;

-- Своевременность: устаревшие записи
SELECT COUNT(*) AS stale_count
FROM products
WHERE updated_at < CURRENT_DATE - INTERVAL '1 year'
  AND status = 'active';
```

### Автоматизация с dbt

```yaml
# В dbt schema.yml — пример тестов качества
models:
  - name: customers
    columns:
      - name: customer_id
        tests:
          - unique
          - not_null
      - name: email
        tests:
          - not_null
          - unique
      - name: inn
        tests:
          - relationships:
              to: ref('contractors')
              field: inn
```

## Сроки хранения: что учесть

Сроки хранения — не произвольные числа, а регуляторные минимумы + деловая необходимость:

| Тип данных | Регуляторный минимум | Основание |
|---|---|---|
| Первичные бухгалтерские документы | 5 лет | ст. 29 ФЗ-402 «О бухучёте» |
| Кадровые документы (трудовые договоры) | 75 лет | Приказ Росархива №236 |
| Документы по налоговому учёту | 5 лет | ст. 23 НК РФ |
| ПДн — до цели обработки | По цели | ФЗ-152 ст. 5 |
| Технические журналы ИБ | 1 год (ФСТЭК) | Приказы ФСТЭК №17, 21 |
| Переписка (деловая) | 3–5 лет | Типовой перечень Росархива |

**Практика**: создайте таблицу сроков хранения по типам данных. Привяжите её к каталогу данных. Настройте автоматическую пометку на удаление/архивирование по истечении срока.

## Уничтожение данных: практические аспекты

### Что значит «уничтожить» данные

«Удалить из таблицы» ≠ уничтожение данных. Данные могут оставаться в:
- резервных копиях (до их перезаписи или истечения срока);
- аналитических хранилищах (DWH/Data Lake);
- логах транзакций;
- архивах почты и мессенджеров;
- у третьих сторон (провайдеры, подрядчики).

**Корректный процесс уничтожения**:
1. Определите все места, где существуют данные (с помощью lineage в каталоге).
2. Удалите из всех систем-потребителей.
3. Удалите из системы-источника.
4. Запланируйте удаление из резервных копий (или дождитесь их ротации).
5. Направьте запрос на удаление третьим сторонам, если они обрабатывают данные.
6. Составьте акт уничтожения.

### Legal Hold

При получении запроса от суда или следствия — процедура уничтожения для конкретных данных приостанавливается немедленно. Юридическая служба определяет объём данных под hold и уведомляет IT и владельцев данных.

## Данные в разработке: практический подход

**Почему нельзя использовать production-данные в dev/test:**
- Нарушение ФЗ-152 (ПДн в незащищённой среде).
- Риск случайного изменения или утечки.
- Проблемы при разборе инцидентов («а кто дал дамп?»).

**Альтернативы:**

| Подход | Инструменты | Когда подходит |
|---|---|---|
| Синтетические данные | Faker (Python), Mockaroo, Syntho | Когда структура важнее реального распределения |
| Data masking | PostgreSQL anon, ARX, Informatica | Когда нужны реальные паттерны, но без PII |
| Подмножество с маскировкой | Custom SQL + маскировка | Большие базы, где нужна репрезентативная выборка |
| Статические фикстуры | JSON/CSV в репозитории | Небольшие справочные данные |
