## 1. Назначение

Настоящая политика устанавливает принципы и требования к управлению данными {{НАЗВАНИЕ_ОРГАНИЗАЦИИ}}: их владению, жизненному циклу, качеству, метаданным и уничтожению.

Данные — стратегический актив организации. Без явного управления этим активом возникают предсказуемые проблемы: неизвестно, кто несёт ответственность за конкретный набор данных, откуда взялись числа в отчёте руководству, почему данные в двух системах расходятся, можно ли безопасно удалить таблицу, которую никто не трогал два года. Эта политика закрывает такие вопросы — не создавая лишней бюрократии, а вводя минимальную необходимую структуру.

Политика применяется совместно с {{ССЫЛКА_НА_ПОЛИТИКУ_КЛАССИФИКАЦИИ}} (классификация данных по конфиденциальности) и {{ССЫЛКА_НА_ПОЛИТИКУ_ПДН}} (обработка персональных данных).

## 2. Область применения

Политика распространяется на:

- все данные, создаваемые, получаемые, обрабатываемые или хранимые {{НАЗВАНИЕ_ОРГАНИЗАЦИИ}} в ходе деятельности: клиентские данные, операционные данные, финансовые данные, данные сотрудников, технические данные;
- все системы и хранилища данных: корпоративные информационные системы, базы данных, хранилища данных (DWH/Data Lake), файловые хранилища, облачные хранилища, резервные копии;
- всех сотрудников, подразделений и подрядчиков, работающих с данными организации.

Требования к конфиденциальности и безопасности данных по классам определяются {{ССЫЛКА_НА_ПОЛИТИКУ_КЛАССИФИКАЦИИ}}.

## 3. Термины и сокращения

| Термин | Определение |
|---|---|
| Владелец данных (Data Owner) | Руководитель, несущий бизнес-ответственность за конкретный домен данных: точность, полноту, соответствие требованиям |
| Стюард данных (Data Steward) | Операционный хранитель данных: отвечает за ежедневное качество, метаданные, соблюдение стандартов внутри домена |
| Домен данных | Логически связанная область данных, закреплённая за одним владельцем (например, «клиентские данные», «финансовые данные», «данные сотрудников») |
| Мастер-данные (Master Data) | Ключевые справочные данные организации, используемые множеством систем: клиенты, продукты, контрагенты, сотрудники |
| Метаданные | Данные о данных: описание, источник, формат, схема, владелец, срок хранения, ограничения |
| Каталог данных | Централизованный реестр датасетов и их метаданных |
| Жизненный цикл данных | Стадии существования данных: создание → хранение → использование → архивирование → уничтожение |
| Lineage (происхождение данных) | Цепочка трансформаций данных от источника до целевой системы |
| Качество данных | Степень соответствия данных требованиям точности, полноты, согласованности, своевременности и актуальности |
| Обезличивание | Необратимое удаление идентифицирующих признаков, после которого данные не могут быть соотнесены с конкретным лицом |
| Псевдонимизация | Замена идентифицирующих признаков псевдонимами при сохранении возможности обратного преобразования |
| DWH | Data Warehouse — хранилище данных для аналитических задач |

## 4. Структура управления данными

### 4.1. Роли и ответственность

Управление данными строится на трёхуровневой структуре:

**{{КОМИТЕТ_ПО_ДАННЫМ}}** (стратегический уровень):
- формирует стратегию управления данными и приоритизирует домены;
- утверждает стандарты качества и метаданных;
- разрешает споры о владении данными между подразделениями;
- контролирует исполнение настоящей политики.

**Владельцы данных ({{ВЛАДЕЛЕЦ_ДАННЫХ_РОЛЬ}})** (доменный уровень):
- несут бизнес-ответственность за свой домен данных;
- утверждают предоставление доступа к данным домена;
- отвечают за соответствие данных требованиям качества и классификации;
- участвуют в ревизии прав доступа и метаданных.

**Стюарды данных ({{СТЮАРД_ДАННЫХ_РОЛЬ}})** (операционный уровень):
- ведут метаданные в {{КАТАЛОГ_ДАННЫХ}};
- контролируют качество данных, фиксируют и эскалируют дефекты;
- документируют lineage и трансформации данных;
- участвуют в проектах интеграции и миграции данных.

### 4.2. Реестр доменов данных

{{КОМИТЕТ_ПО_ДАННЫМ}} ведёт реестр доменов данных с указанием:
- наименования домена и описания состава данных;
- назначенного владельца и стюарда;
- классификации (в соответствии с {{ССЫЛКА_НА_ПОЛИТИКУ_КЛАССИФИКАЦИИ}});
- систем-источников и систем-потребителей.

Реестр пересматривается {{СРОК_РЕВИЗИИ_ДАННЫХ}} и при существенных изменениях бизнес-процессов.

## 5. Жизненный цикл данных

### 5.1. Создание и сбор данных

При создании нового набора данных или начале сбора данных из нового источника:

- определяется домен и назначается владелец данных;
- данные классифицируются до начала их сбора или сразу при создании (см. {{ССЫЛКА_НА_ПОЛИТИКУ_КЛАССИФИКАЦИИ}});
- документируются в {{КАТАЛОГ_ДАННЫХ}}: источник, формат, схема, цель сбора, основание (правовое — для ПДн);
- сбор избыточных данных (больше, чем необходимо для заявленной цели) запрещён — принцип минимальности.

### 5.2. Хранение

- Данные хранятся в системах, соответствующих их классу конфиденциальности.
- Для каждого домена данных определены и задокументированы сроки хранения:

| Тип данных | Минимальный срок хранения | Максимальный срок |
|---|---|---|
| Оперативные / транзакционные | По регуляторным требованиям | {{СРОК_ХРАНЕНИЯ_ОПЕРАТИВНЫХ}} |
| Аналитические / архивные | По регуляторным требованиям | {{СРОК_ХРАНЕНИЯ_АРХИВНЫХ}} |
| Технические журналы | 6 месяцев | {{СРОК_ХРАНЕНИЯ_ЛОГОВ}} |
| Персональные данные | По основанию обработки (ФЗ-152) | До отзыва согласия / цели |

- Данные, для которых срок хранения истёк и отсутствует правовое основание для продолжения обработки, подлежат уничтожению (§5.5).
- Хранение данных вне зарегистрированных систем (локальные диски, личные облачные хранилища, мессенджеры) — нарушение политики для данных выше класса «Общедоступные».

### 5.3. Использование и доступ

- Доступ к данным предоставляется на основании принципа необходимости («нужно знать») и в соответствии с {{ССЫЛКА_НА_ПОЛИТИКУ_ДОСТУПА}}.
- Предоставление доступа к данным домена согласовывается с владельцем данных.
- Использование данных вне заявленных целей (перепрофилирование) требует согласования с владельцем данных и, при необходимости, с {{ССЫЛКА_НА_ПОЛИТИКУ_ПДН}}.
- Передача данных третьим сторонам регулируется договором и требует оценки уровня защиты у получателя.

### 5.4. Передача данных между системами

Интеграции и передача данных между системами:

- документируются как связи в {{КАТАЛОГ_ДАННЫХ}} (lineage);
- соответствуют классу конфиденциальности: данные не передаются в системы с более низким уровнем защиты, чем их класс требует;
- шифруются при передаче в соответствии с {{ССЫЛКА_НА_ПОЛИТИКУ_ИБ}};
- для ПДн: трансграничная передача соответствует требованиям ФЗ-152 ст. 12 и {{ССЫЛКА_НА_ПОЛИТИКУ_ПДН}}.

### 5.5. Архивирование и уничтожение

**Архивирование**: данные, срок оперативного хранения которых истёк, но требующие долгосрочного сохранения (регуляторные обязательства, споры), перемещаются в архив с пониженной доступностью. Владелец данных подтверждает основание для архивирования.

**Уничтожение**: данные, срок хранения которых истёк и основание для сохранения отсутствует, уничтожаются:

- для цифровых носителей: криптографическое стирание (если данные зашифрованы) или перезапись с подтверждением стандарта (DoD 5220.22-M или ГОСТ);
- для физических носителей: шредирование или физическое уничтожение с актом;
- факт уничтожения документируется: что, когда, кем, каким методом;
- уничтожение данных, находящихся под legal hold (судебный запрет, следственные действия), приостанавливается до снятия ограничений.

## 6. Качество данных

### 6.1. Параметры качества

Качество данных оценивается по следующим параметрам:

| Параметр | Определение |
|---|---|
| Точность | Данные отражают реальное состояние объекта |
| Полнота | Обязательные атрибуты заполнены; отсутствие пропусков без оснований |
| Согласованность | Данные об одном объекте не противоречат друг другу в разных системах |
| Своевременность | Данные актуальны на момент использования; задержка обновления не превышает допустимую |
| Уникальность | Отсутствие дублей в реестрах и справочниках |

### 6.2. Целевые показатели и контроль

- Для критичных бизнес-данных (мастер-данные, финансовые данные, данные клиентов) устанавливается целевой показатель качества не ниже {{ПОРОГ_КАЧЕСТВА_ДАННЫХ}}.
- Стюард данных ежемесячно проверяет качество данных в своём домене и фиксирует результаты в {{КАТАЛОГ_ДАННЫХ}}.
- Выявленные дефекты качества категоризируются по критичности и устраняются в сроки:
  - критичные (данные недостоверны и используются в принятии решений) — в течение {{СРОК_УСТРАНЕНИЯ_КАЧЕСТВА}} с момента обнаружения;
  - некритичные — в плановом порядке.

### 6.3. Мастер-данные

Управление мастер-данными требует отдельного внимания:

- для каждого класса мастер-данных (клиенты, продукты, контрагенты, сотрудники) определена система-источник истины (authoritative source);
- изменения в мастер-данных вносятся только через систему-источник;
- механизмы синхронизации мастер-данных с потребляющими системами документируются.

## 7. Метаданные и каталог данных

### 7.1. Обязательные метаданные

Каждый зарегистрированный набор данных (таблица, файл, поток, API) содержит в {{КАТАЛОГ_ДАННЫХ}} следующие метаданные:

| Метаданные | Описание |
|---|---|
| Наименование | Понятное наименование на русском языке |
| Описание | Что содержат данные, для чего используются |
| Домен | К какому домену данных относится |
| Владелец | Ответственный сотрудник (роль/имя) |
| Класс конфиденциальности | По {{ССЫЛКА_НА_ПОЛИТИКУ_КЛАССИФИКАЦИИ}} |
| Источник / происхождение | Откуда данные поступают |
| Срок хранения | Дата или условие уничтожения |
| Статус | Активен / архив / устарел |
| Дата последнего обновления | Автоматически или вручную |

### 7.2. Жизненный цикл метаданных

Метаданные создаются при регистрации нового набора данных и обновляются при изменениях схемы, владельца, назначения или статуса. При уничтожении данных соответствующая запись в каталоге помечается как «удалён» и не удаляется из каталога — метаданные сохраняются для поддержания lineage. Сами данные при этом уничтожаются в соответствии с §5.5.

## 8. Данные в разработке и аналитике

### 8.1. Данные в среде разработки и тестирования

- В среду разработки и тестирования загружаются только обезличенные или синтетические данные.
- Использование реальных производственных данных (в т.ч. ПДн) в разработке и тестировании **запрещено**. В исключительных случаях — при невозможности воспроизвести задачу на обезличенных данных — возможно временное использование реальных данных только при одновременном выполнении условий: явное решение владельца данных и {{ОТВЕТСТВЕННЫЙ_ЗА_ИБ}}, изоляция среды по уровню защиты производственной, документирование и своевременное уничтожение копии. Подробнее — {{ССЫЛКА_НА_ПОЛИТИКУ_РАЗРАБОТКИ}}.
- Средства генерации тестовых данных и обезличивания (data masking) применяются там, где это технически реализуемо.

### 8.2. Аналитические данные и отчётность

- Аналитические отчёты и дашборды, использующие данные с ограниченным доступом, защищаются аналогично исходным данным.
- Агрегированные данные, из которых невозможно восстановить персональные или конфиденциальные данные, могут иметь более низкий класс конфиденциальности — при подтверждении стюардом данных.

### 8.3. Данные для обучения ИИ-моделей

Использование корпоративных данных для обучения ИИ-систем регулируется дополнительно {{ССЫЛКА_НА_ПОЛИТИКУ_ИИ}}:
- требует классификации данных и оценки возможности re-identification;
- персональные данные для обучения — только при наличии правового основания;
- fine-tuning через внешние платформы — только при заключённом поручении на обработку данных.

## 9. Данные в облаке

Хранение и обработка данных в облачных сервисах регулируется {{ССЫЛКА_НА_ПОЛИТИКУ_ОБЛАКА}} с учётом требований настоящей политики:

- данные не размещаются в облачных системах без предварительной классификации и согласования владельца;
- физическое расположение данных документируется; для ПДн граждан РФ обязательно хранение в РФ (ч. 5 ст. 18 ФЗ-152);
- данные в облаке включаются в реестр и каталог с указанием облачного провайдера и региона.
