# Руководство по применению — POL-CLD-001 Политика облачной безопасности

## Для кого этот документ

Для CISO, облачных администраторов и DevOps-инженеров, которые внедряют требования безопасности в облачной инфраструктуре организации.

---

## Шаг 1. Инвентаризация облачных сервисов

Прежде чем применять политику, нужно знать, что уже используется. Типичная картина: официально одобрены 3–5 сервисов, фактически используются 15–30 (Shadow IT).

**Как обнаружить:**
- Анализ корпоративных кредитных карт и счетов на предмет подписок.
- Анализ DNS-запросов и интернет-трафика (с МЭ или прокси).
- Опрос подразделений: «какими облачными сервисами вы пользуетесь?»
- Если используется CASB (Cloud Access Security Broker) — он уже это делает.

Всё найденное оцените по критериям §5.2. Сервисы, не прошедшие оценку, либо одобряются с компенсирующими мерами, либо мигрируются на одобренные альтернативы.

## Шаг 2. Критерии допуска CSP — практика

**Минимальный набор для любого CSP:**
- Шифрование данных в покое и при передаче.
- MFA для административного доступа.
- Журналы аудита API-вызовов (аналог CloudTrail).
- Возможность экспорта всех данных.
- Соглашение о конфиденциальности и, при обработке ПДн, поручение на обработку.

**Для конфиденциальных данных дополнительно:**
- ISO 27001 или SOC 2 Type II сертификация.
- Управляемые клиентом ключи (CMK/BYOK).
- Подтверждённое местонахождение серверов в РФ (для ПДн граждан РФ).

**Красные флаги:**
- Провайдер не готов подписать поручение на обработку ПДн.
- Нет возможности экспортировать данные без дополнительной оплаты.
- Нет аудита доступа к вашим данным со стороны сотрудников провайдера.
- Нет SLA по доступности.

## Шаг 3. Локализация ПДн — разбираем детали

Это самое сложное требование политики, и здесь много заблуждений.

**Что говорит закон:**
Ст. 18.1 ч. 5 ФЗ-152: при сборе ПДн граждан РФ оператор обязан обеспечить запись, систематизацию, накопление, хранение, уточнение, извлечение этих ПДн с использованием баз данных, находящихся на территории РФ.

**Что это означает на практике:**
- База данных с ПДн граждан РФ должна быть физически в РФ.
- Резервные копии этой базы также должны быть в РФ (или соблюдать требование при восстановлении).
- Передача ПДн за рубеж (трансграничная передача) для других целей — по ст. 12 ФЗ-152, с уведомлением РКН.

**Что НЕ запрещено:**
- Иностранные CSP, у которых есть датацентры в РФ (если хранить ПДн именно там).
- Передача обезличенных данных (не ПДн) за рубеж.
- Передача ПДн за рубеж с согласия субъекта (в определённых случаях).

**Актуальные российские CSP:**
- Яндекс Облако (yandex.cloud) — датацентры в РФ, сертифицировано.
- VK Cloud (mcs.mail.ru) — датацентры в РФ.
- Selectel — датацентры в РФ.
- SberCloud — датацентры в РФ.
- Ряд иностранных CSP открыли зоны в РФ, но уточняйте актуальность с учётом санкционных ограничений.

## Шаг 4. IAM в облаке — распространённые ошибки

**Ошибка 1: root-аккаунт используется повседневно**
Root/owner — бог облака, у которого нет ограничений. Использование его для повседневных задач — огромный риск. Создайте отдельные роли с ограниченными правами и уберите root в сейф (длинный пароль, MFA, ключи доступа не создавать).

**Ошибка 2: один IAM-пользователь на команду**
«Мы все знаем пароль admin@company» — полная потеря аудитируемости и невозможность быстро отозвать доступ при увольнении. Индивидуальные учётные записи обязательны.

**Ошибка 3: ключи доступа в коде**
Один из самых распространённых векторов утечек. Ключ, закоммиченный в публичный репозиторий, обнаруживается боттами за считанные минуты. Используйте:
- IAM Roles вместо ключей (для ресурсов внутри облака).
- Secrets Manager / Vault для хранения ключей.
- `git secrets` или pre-commit hooks для предотвращения коммита секретов.

**Ошибка 4: избыточные права «на всякий случай»**
Политика «дать Administrator чтобы точно работало» — нормальная на старте и катастрофическая в производстве. Используйте принцип наименьших привилегий и инструменты анализа (AWS IAM Access Analyzer, Azure AD Access Reviews).

## Шаг 5. Безопасные конфигурации — с чего начать

**Быстрые победы (можно сделать сегодня):**
1. Включите MFA на root/owner и всех администраторских аккаунтах.
2. Проверьте все S3-бакеты/Blob-контейнеры/Object Storage-бакеты — нет ли публичного доступа.
3. Включите CloudTrail/Audit Logs и убедитесь, что они не удаляются.
4. Проверьте Security Groups — нет ли правил 0.0.0.0/0 на порты 22 (SSH) или 3389 (RDP).

**Автоматизация:**
- AWS: AWS Security Hub + Config Rules + GuardDuty.
- Azure: Microsoft Defender for Cloud + Azure Policy.
- GCP: Security Command Center.
- Яндекс Облако: Yandex Security Solution, встроенные политики.
- Универсальные CSPM: Wiz, Orca Security, Prisma Cloud.
- Open Source: CloudCustodian, Prowler (AWS), ScoutSuite.

## Шаг 6. IaC и DevSecOps

**Почему IaC важен для безопасности:**
Без IaC конфигурация создаётся вручную через консоль — нет истории изменений, нет повторяемости, нет проверок безопасности. С IaC (Terraform, Pulumi, Ansible) конфигурация хранится в git, проходит code review и может автоматически проверяться на ошибки безопасности.

**Инструменты статического анализа IaC:**
- tfsec / Terrascan / Checkov — для Terraform.
- cfn-nag / cfn-lint — для CloudFormation.
- kics — универсальный, поддерживает большинство форматов.

**Минимальный pipeline безопасности:**
1. Pre-commit: проверка на секреты (git-secrets, detect-secrets).
2. PR: статический анализ IaC (Checkov/tfsec).
3. Deploy: применение только через pipeline (не вручную в продакшене).

## Шаг 7. Реагирование на типичные инциденты облака

**Открытый бакет с данными:**
1. Немедленно закрыть публичный доступ.
2. Оценить, какие данные были открыты и как долго.
3. Если ПДн граждан РФ — запустить процедуру уведомления РКН (24ч/72ч).
4. Журналы доступа проверить на факт скачивания.

**Компрометация IAM-учётной записи:**
1. Немедленно деактивировать учётную запись.
2. Отозвать все активные сессии и ключи доступа.
3. Проверить журналы за последние 90 дней на предмет подозрительных действий.
4. Проверить все ресурсы, к которым имела доступ учётная запись.
5. Провести ротацию ключей связанных сервисных аккаунтов.

**Утечка ключей API в публичный репозиторий:**
1. Немедленно отозвать ключ (не ждите уточнения — за минуты ключи находят боты).
2. Создать новый ключ.
3. Проверить журналы на использование ключа посторонними.
4. Убрать ключ из истории git (git filter-branch или BFG Repo Cleaner).

## Типичные ошибки при внедрении

**1. «Облако — это ответственность провайдера»**
Самое опасное заблуждение. Большинство инцидентов — неверная конфигурация на стороне клиента, а не взлом CSP. Таблица в §4 показывает, что за данные и IAM отвечает всегда клиент.

**2. Политика есть, аудита нет**
Без регулярной проверки реального состояния конфигурации политика остаётся на бумаге. CSPM решает это автоматически.

**3. Shadow IT игнорируется**
Если разработчики используют Dropbox, Google Drive или Notion с корпоративными данными без ведома ИБ — политика не работает. Выявление Shadow IT — часть внедрения политики.

**4. MFA только для людей**
Сервисные аккаунты с долгосрочными ключами без ротации — распространённый вектор атаки. Переходите на роли и временные токены.

## Проверочный список при внедрении

- [ ] Проведена инвентаризация всех используемых облачных сервисов
- [ ] Все сервисы внесены в реестр или запланирована миграция
- [ ] Для каждого CSP с ПДн оформлено поручение на обработку
- [ ] ПДн граждан РФ хранятся в РФ (подтверждено документально)
- [ ] MFA включена для всех учётных записей с правами изменения конфигурации
- [ ] Root/owner аккаунт защищён и не используется для повседневных задач
- [ ] Все публичные бакеты/хранилища проверены
- [ ] CloudTrail/Audit Logs включены и хранятся в отдельном хранилище
- [ ] Security Groups проверены на отсутствие открытых портов управления
- [ ] Секреты вынесены из кода и хранятся в Secrets Manager
- [ ] CSPM-мониторинг настроен
- [ ] Процедура ревизии прав доступа включена в календарь
