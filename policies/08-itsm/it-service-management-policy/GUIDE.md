# Руководство по применению POL-SVC-001

## Как использовать этот шаблон

### Шаг 1. Определите систему учёта заявок

Политика работает только при наличии инструмента. Без него «единая точка контакта» останется лозунгом. Заполните `{{СИСТЕМА_УЧЁТА_ЗАЯВОК}}` — это может быть:

- **Коммерческое**: Jira Service Management, ServiceNow, Zendesk, Freshservice
- **Open Source**: OTRS/Znuny, Zammad, osTicket
- **Российское**: 1С:ITIL, NAUMEN Service Desk, Hive
- **Упрощённый вариант**: корпоративный мессенджер + spreadsheet (только для небольших команд до ~20 IT-специалистов; плохо масштабируется)

### Шаг 2. Определите реалистичные SLA

Ошибка №1 при внедрении — взять «красивые» цифры из интернета (P1 = 15 мин реакция, 2 часа разрешение) без понимания текущих возможностей. Рекомендуемый подход:

1. Соберите данные из текущей системы (или оцените экспертно) — сколько реально занимает обработка инцидентов по типам
2. Задайте SLA на 20–30% лучше текущего медианного значения — это достижимая цель с усилиями
3. Через 3–6 месяцев пересмотрите и ужесточите, если команда стабильно выполняет

**Ориентиры для заполнения плейсхолдеров (адаптируйте под себя):**

|---|---|---|---|

| `{{SLA_РАЗРЕШЕНИЕ_КРИТИЧЕСКИЙ}}` | 4 часа | 2 часа | 1 час |

### Шаг 3. Создайте каталог услуг

Не нужно сразу описывать 100 услуг. Начните с минимального жизнеспособного каталога:

- Выпишите 10–15 самых частых типов обращений (по данным из системы или экспертно)
- Для каждого определите: кто может запросить, кто выполняет, какой SLA
- Добавьте раздел «прочие запросы» для нестандартных ситуаций
- Расширяйте каталог итерационно — раз в квартал добавляйте по 3–5 новых услуг

### Шаг 4. Запустите процесс PIR

Post-Incident Review для P1 — это навык, который нужно нарабатывать. Частые ошибки:

- **PIR превращается в поиск виноватых** — это убивает честность и ценность разбора. Установите правило: цель PIR — найти системные причины, не людей.
- **PIR откладывается** — политика требует завершить в 5 рабочих дней. Назначьте ответственного в момент закрытия P1-инцидента.
- **PIR не приводит к изменениям** — отчёт PIR должен содержать конкретные задачи с ответственными и сроками, вносимые в backlog.

## Частые ошибки внедрения

### «Двери IT открыты»

Многие IT-директора гордятся тем, что «у нас можно прийти напрямую». Это снижает барьер, но разрушает SLA-систему: незарегистрированная работа не измеряется, не передаётся другому специалисту, создаёт bus factor. Политика прямо говорит: незарегистрированная заявка не имеет SLA. Коммуницируйте это пользователям заблаговременно.

### Завышенные SLA без ресурсов

Обязательства P1 = «15 минут реакция, 2 часа разрешение» требуют дежурного инженера 24×7 или хотя бы режима on-call. Если ресурсов нет — честные SLA лучше невыполнимых. Невыполненный SLA разрушает доверие сильнее, чем изначально скромное обещание.

### CMDB как разовый проект

Заполнили CMDB при внедрении — и забыли обновлять. Через год данные устарели, CMDB не используется при диагностике. Автоматизируйте обновление где возможно (через SCCM, Ansible, облачные API), остальное — через процесс Change Management.

### Метрики ради метрик

Ежемесячный отчёт, который никто не читает — потраченное время. Убедитесь, что IT-директор представляет отчёт менеджменту и тот реально принимает на основе него решения (ресурсы, приоритеты, инвестиции).

## Адаптация для малого бизнеса

Для организаций до 100 сотрудников с IT-командой 1–3 человека полный ITIL избыточен. Допустимые упрощения:

- Объединить P3 и P4 в один приоритет «обычный»
- Убрать формальный процесс управления проблемами, оставить только анализ повторяющихся инцидентов
- Упростить каталог до 5–7 категорий без детального описания каждой услуги
- PIR только для P1 (которых, вероятно, 1–2 в год)
- Ежеквартальный отчёт вместо ежемесячного

## Адаптация для аутсорсинговой модели

Если IT полностью на аутсорсинге:

- Раздел §8.2 («SLA с внешними подрядчиками») становится центральным: вся политика реализуется через договорные SLA
- Добавьте раздел о порядке эскалации к подрядчику и о праве аудита SLA
- Целевые показатели 95%/90% должны быть зеркальными в договоре с подрядчиком
- Определите внутренний Service Owner для каждой договорной услуги — человека, отвечающего за мониторинг качества подрядчика

## Связь с ISO/IEC 20000-1 и ITIL

Если организация планирует сертификацию по ISO/IEC 20000-1:2018:

- Эта политика — верхнеуровневый документ, соответствующий требованиям п. 5.2 (политика системы управления услугами) и п. 8.2 (каталог услуг)
- Дополнительно потребуются: процедуры управления инцидентами (п. 8.6), запросами (п. 8.5), проблемами (п. 8.7), конфигурациями (п. 8.8), изменениями (п. 8.4), уровнями сервиса (п. 8.3)
- ITIL 4 предоставляет практики, а не шаблоны документов — используйте как источник идей, а не как требования
