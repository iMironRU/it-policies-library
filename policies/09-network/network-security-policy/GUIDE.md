# Руководство по применению — POL-NET-001 Политика сетевой безопасности

## Для кого этот документ

Для сетевых администраторов, специалистов по ИБ и IT-менеджеров, которые внедряют или адаптируют политику сетевой безопасности в своей организации.

---

## Шаг 1. Заполнение плейсхолдеров

**Критичные для смысла:**

- `{{ПЕРИОД_РЕВИЗИИ_ПРАВИЛ_FIREWALL}}` — рекомендуется «раз в квартал». Чем активнее меняется инфраструктура, тем чаще.
- `{{СРОК_ХРАНЕНИЯ_СЕТЕВЫХ_ЖУРНАЛОВ}}` — минимум 6 месяцев по требованиям ФСТЭК №21 (раздел РЕГ). Для систем, обрабатывающих ПДн, журналы доступа к ПДн хранятся не менее 3 лет (ч. 4 ст. 21 ФЗ-152). Практический ориентир: 12 месяцев — хорошо для большинства организаций.
- `{{СТАНДАРТ_WIFI_КОРПОРАТИВНЫЙ}}` — WPA3-Enterprise предпочтительнее, WPA2-Enterprise допустим. WPA2-Personal (PSK) для корпоративной сети — слишком слабо.
- `{{СРОК_ОБРАБОТКИ_ЗАЯВКИ_НА_ПРАВИЛО}}` — обычно 3–5 рабочих дней. Для экстренных изменений укажите отдельный сокращённый срок (1 рабочий день).

## Шаг 2. Адаптация схемы сетевых зон

Таблица в разделе 5.1 — отправная точка. Реальная топология в большинстве организаций будет отличаться. Типичные варианты:

**Малая организация (до 50 человек):**
- Обычно нет выделенного управляющего сегмента.
- DMZ может совмещать несколько типов сервисов.
- Гостевая сеть — отдельная SSID на том же маршрутизаторе.
- Минимальный набор: хотя бы внешняя / внутренняя / гостевая.

**Средняя организация (50–500 человек):**
- Стоит выделить серверный сегмент отдельно.
- Управляющий сегмент желателен хотя бы как отдельный VLAN с ограниченным доступом.
- Dev/test среда — обязательная изоляция от prod.

**Крупная организация / с ПДн высокого уровня защищённости:**
- Полный набор зон, включая выделенные сегменты для ПДн.
- Контроль East-West трафика (не только периметр) — микросегментация или NGFW.
- Управляющая сеть с out-of-band доступом (отдельный физический интерфейс или выделенный VLAN).

## Шаг 3. Baseline конфигурации сетевого оборудования

Раздел 9.1 описывает требования к baseline, но не даёт конкретных технических параметров — это намеренно, так как они зависят от вендора. Что необходимо сделать:

1. Составить перечень типов оборудования (Cisco, Juniper, Mikrotik, Huawei, FortiGate и т.д.).
2. Для каждого типа разработать отдельный технический документ (hardening guide) с конкретными командами.
3. Хранить baseline конфигурации в системе контроля версий или CMDB.
4. Периодически сверять фактические конфигурации с baseline (автоматизируется через Ansible, RANCID, Oxidized или аналогичные инструменты).

**Хорошие источники для baseline:**
- CIS Benchmarks для конкретных вендоров (cisecurity.org)
- Рекомендации ФСТЭК по защите информации в ИСПДн и ГИС
- Vendor security hardening guides (Cisco SAFE, Fortinet Security Best Practices)

## Шаг 4. Управление правилами МЭ на практике

**Частые проблемы:**

- **«Временные» правила, живущие годами.** Решение: при создании правила фиксировать дату истечения и ставить задачу на удаление. В таск-трекер или напоминание в календаре.
- **Правила без обоснования.** Без контекста при ревизии невозможно понять, нужно ли правило. Требуйте тикет/заявку для каждого правила.
- **Избыточно широкие правила.** «Разрешить всё из бухгалтерии в интернет» — если сотруднику нужен доступ только к определённому SaaS, лучше ограничить по dst.

**Инструментарий для ревизии:**
- Большинство NGFW-решений (Fortinet, Palo Alto, Check Point) имеют встроенный анализатор политик с выявлением теневых (shadowed), избыточных и неиспользуемых правил.
- При отсутствии встроенного инструмента — ручная ревизия по выгрузке реестра правил в таблицу с полями: правило / обоснование / дата создания / последняя активность / ответственный.

## Шаг 5. VPN — выбор решения

Шаблон намеренно не привязан к конкретному VPN-продукту. При выборе учтите:

| Параметр | Рекомендации |
|---|---|
| Протокол | IKEv2/IPsec, WireGuard, OpenVPN — все приемлемы; PPTP/L2TP без IPsec — запрещены |
| МФА | TOTP, push-уведомления, аппаратные ключи (FIDO2) — любое из них лучше, чем только пароль |
| Split tunneling | По умолчанию отключайте; включайте только для обоснованных исключений (например, видеоконференции) |
| Журналирование | Подключения, имя пользователя, IP-адрес клиента, длительность сессии |
| Отзыв доступа | VPN-учётные данные должны быть связаны с корпоративной директорией (AD/LDAP) для автоматического отзыва |

**Про СКЗИ и ФСБ:** если по корпоративному VPN передаются ПДн с уровнем защищённости УЗ-1 и выше, или работаете с государственными ИС, может потребоваться VPN-решение с сертифицированными средствами СКЗИ (КС1/КС2) по требованиям ФСБ №378. Уточните с юристом и CISO.

## Шаг 6. Беспроводные сети

**WPA2-Enterprise vs WPA2-Personal:**
- WPA2-Personal (PSK): один пароль для всех. Если пароль утёк — меняется для всех. Приемлемо для гостевой сети, неприемлемо для корпоративной.
- WPA2-Enterprise: каждый пользователь аутентифицируется своими корпоративными учётными данными через RADIUS. Отзыв доступа немедленный. Рекомендуется для корпоративной сети.

**RADIUS-сервер:**
- Windows Server: NPS (Network Policy Server) — бесплатно в рамках Windows Server.
- FreeRADIUS — open-source, для Linux-среды.
- Облачные варианты: Cisco ISE, Aruba ClearPass, JumpCloud, Azure AD с NPS.

**Rogue AP:**
- Периодическое сканирование можно автоматизировать через WIPS (Wireless Intrusion Prevention System) — функция многих корпоративных Wi-Fi-платформ (Cisco, Aruba, Fortinet).
- Без WIPS: плановое сканирование раз в квартал + реакция на жалобы пользователей.

## Шаг 7. Мониторинг — с чего начать

Журналирование «всего» с первого дня нереалистично для малых организаций. Приоритизация:

**Минимальный уровень (должно быть у всех):**
- МЭ: заблокированные входящие соединения с периметра.
- VPN: неудачные аутентификации.
- DNS: запросы к известным вредоносным доменам (если есть DNS-фильтрация).

**Стандартный уровень:**
- МЭ: весь разрешённый трафик между зонами.
- VPN: все подключения (успешные и неудачные).
- Изменения конфигурации оборудования.

**Расширенный уровень:**
- NetFlow для всего периметрного и inter-VLAN трафика.
- IDS/IPS с настроенными сигнатурами.
- Полная интеграция в SIEM с корреляцией.

## Типичные ошибки при внедрении

**1. Сегментация есть, но трафик не проверяется**
VLAN без МЭ между ними — не сегментация с точки зрения безопасности. Атака lateral movement легко преодолеет VLAN-границу через уязвимые устройства. Добавляйте МЭ или NGFW для inter-VLAN трафика.

**2. Управляющие интерфейсы доступны из пользовательской сети**
SSH к коммутатору из рабочей сети — удобно администратору и удобно злоумышленнику с захваченным ноутбуком. Ограничьте доступ к управляющим интерфейсам отдельным VLAN или jump-хостом.

**3. Пересмотр правил МЭ «когда-нибудь потом»**
Ревизия правил МЭ — одно из наиболее пренебрегаемых мероприятий. Без регулярной ревизии база правил становится неуправляемой. Планируйте как регулярную задачу в календаре.

**4. Один пароль на всё оборудование**
Если единственный пароль администратора сетевого оборудования известен десяти людям — это не контроль. Используйте RADIUS/TACACS+ для централизованной аутентификации администраторов оборудования.

**5. Split tunneling «для удобства»**
Включённый split tunneling для всех пользователей означает, что угрозы на домашнем устройстве не блокируются корпоративным периметром. Решение: DNS-over-VPN с full tunnel или жёсткий список исключений.

## Особенности для ПДн (ФЗ-152)

- Серверы с ПДн должны находиться в выделенном сегменте с журналированием всех сетевых обращений.
- Передача ПДн по незащищённым сетям (в том числе внутри организации) требует шифрования.
- Журналы сетевых событий, связанных с доступом к ПДн, хранятся не менее 3 лет (ч. 4 ст. 21 ФЗ-152).
- Для ИСПДн с УЗ-1 и УЗ-2 ФСТЭК устанавливает классы МЭ (МЭ.2–МЭ.4 и выше) — уточняйте по приказу №21.

---

## Особенности для КИИ (ФЗ-187)

Для объектов критической информационной инфраструктуры:
- Требования к сегментации, мониторингу и реагированию на инциденты дополнительно регулируются приказом ФСТЭК №239.
- Обязательное взаимодействие с НКЦКИ (ГосСОПКА) при инцидентах.
- Технические средства обнаружения атак (ТСОА) подпадают под требования к сертификации.
