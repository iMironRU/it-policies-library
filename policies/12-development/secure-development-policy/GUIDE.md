# Руководство по применению POL-DEV-001

## Кому читать этот файл

Этот файл — для того, кто адаптирует шаблон под свою организацию: технического директора, руководителя разработки или ответственного за ИБ.

---

## Шаг 1 — Оцените масштаб применения

Политика написана с прицелом на организации с командой разработки от 3 до 50 человек. Прежде чем редактировать, ответьте на вопросы:

**Что разрабатывается?**
- Веб-приложения с внешними пользователями → все разделы, плюс обязательный DAST
- Внутренние инструменты → можно упростить §6.3.2–6.3.3
- Мобильные приложения → добавьте требования к подписи артефактов и сертификатам

**Есть ли обработка персональных данных?**
- Да → требования §6.3.3 (пентест) становятся обязательными; свяжите с POL-DAT-001
- Нет → §6.3.3 можно пометить как рекомендательный

**Есть ли внешние подрядчики-разработчики?**
- Да → добавьте в договоры с подрядчиками ссылку на эту политику и требование её соблюдения (§10)

## Шаг 3 — Расставьте приоритеты внедрения

Не обязательно внедрять всё сразу. Рекомендуемый порядок по соотношению усилий и пользы:

**Неделя 1 — нулевой уровень (ничего не стоит):**
1. Включить защиту веток в репозитории (§5.3) — 15 минут в настройках
2. Добавить `.gitignore` для `.env` файлов — 5 минут
3. Включить GitHub Secret Scanning, если используете GitHub — 1 клик

**Первый месяц — автоматические проверки в CI:**
4. Добавить SAST в CI/CD pipeline (§6.3.1)
5. Добавить SCA / Dependabot (§7.2)
6. Настроить хранение секретов в vault (§8.1)

**Первый квартал — процессы:**
7. Ввести обязательный code review (§5.4)
8. Провести обучение по OWASP Top 10 (§11)
9. Определить перечень критичных приложений для пентеста

---

## Шаг 4 — Адаптируйте SLA по уязвимостям

Сроки в §9.1 — рекомендательные. При адаптации учтите:

- **Для малого бизнеса** без продакшен-дежурных 72 часа на Critical может быть нереалистично ночью в пятницу → добавьте оговорку «рабочих часов» или поднимите до «в первый рабочий день»
- **Для SaaS с 24/7** → 72 часа адекватны
- **Для внутренних инструментов** без внешнего доступа → можно удвоить все сроки

## Шаг 5 — Частые ошибки при внедрении

### Ошибка 1: Блокировка всего на SAST с первого дня
SAST на новой кодовой базе выдаёт сотни предупреждений. Не блокируйте CI на старом коде сразу. Подход:
1. Запустите SAST в режиме «только уведомление» (non-blocking)
2. Закройте накопившийся долг за 1–2 спринта
3. Переведите в блокирующий режим

### Ошибка 2: Политика без инструментов
«Секреты хранить в vault» без реально настроенного vault приводит к тому, что разработчики продолжают класть секреты в `.env`-файлы. Инфраструктура должна быть готова до требований.

### Ошибка 3: Пентест вместо базовых практик
Пентест выявляет уязвимости, но не исправляет процессы. Если SAST не настроен, пентест найдёт те же проблемы через год. Приоритет — автоматические проверки в CI.

### Ошибка 4: Устаревший список зависимостей
SCA не работает, если lock-файлы не обновляются. Настройте автоматические PR на обновление зависимостей (Dependabot / Renovate).

## Связь с регуляторикой

### ISO/IEC 27001:2022
Разделы A.8.25–A.8.32 полностью покрываются этой политикой. При прохождении сертификации используйте §6 как основу для Statement of Applicability по домену разработки.

### ФЗ-152 (персональные данные)
Если ПО обрабатывает ПДн, ст. 19 обязывает принять меры, исключающие несанкционированный доступ. Эта политика является частью выполнения этого требования. Свяжите с POL-DAT-001.

### ГОСТ Р 56939-2016
Российский стандарт безопасной разработки. Совместим с этой политикой. При необходимости соответствия ГОСТ добавьте явную ссылку в §14 и маппинг в metadata.yml.
