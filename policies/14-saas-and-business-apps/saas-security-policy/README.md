# POL-SAA-001 — Политика безопасности SaaS и бизнес-приложений

**Maturity:** ◆ Standard  
**Владелец:** CISO / CDO  
**Статус:** draft

---

## Зачем нужна эта политика

Среднестатистическая компания использует более 100 SaaS-инструментов — и большинство из них появляются без ведома IT и ИБ. Сотрудник регистрируется в Notion, загружает туда проектные документы, уходит из компании — и данные остаются. Разработчик подключает Slack к внутренней системе через Zapier — и токен хранится в открытом виде.

Без политики нет ответов на вопросы:
- Какие приложения у нас вообще используются?
- Кто ответственен за каждое из них?
- Куда можно выгружать ПДн клиентов, а куда нельзя?
- Что происходит с доступом уволенного сотрудника ко всем приложениям?
- Кто проверял, что вендор не хранит наши данные в стране, которая нам не подходит?

Эта политика отвечает на все эти вопросы и создаёт управляемую экосистему приложений без бюрократических барьеров, замедляющих бизнес.

## Ключевые решения при внедрении

1. **Реестр приложений**: с нуля или интеграция с существующим CMDB? Хорошим компромиссом бывает таблица в Confluence или Notion — главное не точность инструмента, а полнота данных.

2. **IdP и SSO**: без корпоративного IdP (Azure AD / Entra ID, Okta, Keycloak) большинство требований политики невозможно автоматизировать. Если IdP ещё нет — это первый шаг.

3. **CASB или прокси**: для обнаружения теневых IT нужен либо CASB (Netskope, Microsoft Defender for Cloud Apps, Zscaler), либо форвардный прокси с фильтрацией. Без этого выявление Shadow IT — ручной процесс.

4. **DPA с вендорами**: для всех приложений, обрабатывающих ПДн, требуется договор поручения обработки. Это процесс с юридическим отделом — закладывайте время.

5. **Порог обязательного SSO**: слишком строгий порог (например, 1 пользователь) парализует работу. Рекомендуем начинать с 5–10 пользователей и снижать по мере зрелости.
