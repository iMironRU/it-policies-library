# GUIDE — POL-SAA-001 Политика безопасности SaaS и бизнес-приложений

Руководство по внедрению: как запустить управление SaaS с нуля, выбрать инструменты и избежать типичных ловушек.

---

## С чего начать: дорожная карта

### Этап 1 (1–4 недели): видимость

1. **Инвентаризация «снизу вверх»**: попросите каждый отдел перечислить инструменты, которые они используют. Опрос в Google Forms / Яндекс Формах займёт 30 минут, даст 80% картины.
2. **Анализ финансовых транзакций**: выгрузка с корпоративных карт и через бухгалтерию — покажет оплачиваемые SaaS-подписки.
3. **Анализ DNS / прокси-логов** (при наличии): выявит сервисы, к которым обращаются сотрудники.
4. Составьте первичный реестр. Даже таблица в Excel лучше, чем ничего.

### Этап 2 (1–3 месяца): порядок

5. **Классифицируйте** приложения по уровням риска (§4 шаблона). Начните с очевидных: CRM, HRM, почта — критический; файловые хранилища, видеоконференции — высокий.
6. **Назначьте бизнес-владельцев** для каждого приложения уровня «Критический» и «Высокий».
7. **Настройте SSO** для топ-20 приложений по числу пользователей. SCIM — для тех, кто поддерживает.
8. Разработайте процедуру согласования новых инструментов — достаточно формы в ITSM или письма на почту ИБ.

### Этап 3 (3–12 месяцев): зрелость

9. **Разберитесь с DPA**: пройдитесь по всем приложениям, обрабатывающим ПДн, и оформите договоры поручения обработки.
10. **Автоматизируйте offboarding**: настройте, чтобы удаление пользователя из IdP автоматически деактивировало его во всех SCIM-интегрированных приложениях.
11. **Внедрите CASB или категоризацию трафика** для систематического обнаружения Shadow IT.
12. Проведите первую ежегодную ревизию реестра.

## Типичные ловушки

### «У нас нет Shadow IT — мы всё контролируем»

Практически всегда неверно. В организации из 50 человек обычно обнаруживается 30–50 неизвестных IT-команде SaaS-инструментов. Начните с DNS-анализа или установки CASB в режиме аудита — результат удивит.

### «SSO требует бюджета, которого нет»

Многие популярные SaaS предлагают бесплатную SSO-интеграцию (Notion, Figma, Slack и др.). Платный IdP (Okta, Azure AD P1) окупается экономией времени на onboarding/offboarding при штате от 50+ человек. До этого порога — Keycloak (open source) или бесплатный тариф Azure AD.

### «DPA с американскими вендорами невозможно»

Большинство крупных SaaS-вендоров (Google, Microsoft, Atlassian, Salesforce) предлагают стандартные DPA/DPA-addendum на сайте или по запросу. Для вендоров без DPA — это риск, который нужно принять осознанно или отказаться от сервиса.

### «Всё хранится в РФ»

Проверьте. Даже российские SaaS-компании часто используют зарубежную инфраструктуру (AWS Frankfurt, Google Europe). Данные о стране хранения должны быть в DPA или в документации вендора.

## Классификация приложений на практике

Используйте этот чеклист для быстрой классификации нового приложения:

```
1. Приложение будет обрабатывать персональные данные (ФИО, email, телефон, адрес)?
   → Да: уровень не ниже «Критический»

2. Приложение будет хранить финансовые данные, коммерческую тайну?
   → Да: уровень не ниже «Критический»

3. Приложение будет хранить внутренние документы, переписку, проекты, код?
   → Да: уровень не ниже «Высокий»

4. Приложение будет хранить только публичную информацию?
   → Уровень «Низкий»

5. В приложении будет работать ≥ N пользователей?
   → Если да: SSO обязателен
```

## Оценка безопасности вендора: что проверять

Минимальный чеклист для оценки нового приложения уровня «Высокий»:

```
[ ] Наличие актуальной политики конфиденциальности (ссылка: ___)
[ ] Наличие DPA / Data Processing Agreement (или возможность его заключить)
[ ] Страна хранения данных: ___; соответствует ли требованиям РФ?
[ ] Шифрование в транзите: TLS 1.2+ (проверить через SSL Labs или документацию)
[ ] Шифрование at rest: указано в документации?
[ ] Наличие SOC 2 Type II, ISO 27001 или аналога: ___
[ ] Поддержка SSO (SAML/OIDC): Да / Нет
[ ] Поддержка SCIM: Да / Нет
[ ] Экспорт данных: как? в каком формате?
[ ] Удаление данных после расторжения: в течение скольки дней?
[ ] Программа Responsible Disclosure / Bug Bounty: Да / Нет
[ ] Последний известный инцидент с данными: ___ (проверить HaveIBeenPwned, новости)
```

## Автоматизация offboarding через SCIM

SCIM (System for Cross-domain Identity Management) — стандарт для автоматической синхронизации пользователей. При деактивации пользователя в IdP все SCIM-интегрированные приложения автоматически деактивируют его учётную запись.

**Приложения с хорошей поддержкой SCIM:**
- Slack, Notion, Figma, Asana, Monday.com
- Salesforce, HubSpot, Zendesk
- GitHub, GitLab, Atlassian (Jira/Confluence)
- Zoom, Google Workspace, Microsoft 365

**Настройка в Azure AD / Entra ID:**
1. Перейдите в Enterprise Applications → выберите приложение
2. Вкладка Provisioning → Automatic
3. Введите SCIM endpoint и token приложения
4. Настройте маппинг атрибутов

**Настройка в Okta:**
1. Applications → выберите приложение
2. Вкладка Provisioning → Configure API Integration
3. Enable API integration, введите данные вендора
4. Включите Deactivate Users и Sync Password при необходимости

## Реестр приложений: минимальная структура

Если нет CMDB — используйте таблицу со следующими столбцами:

| Поле | Тип | Описание |
|---|---|---|
| Название | Текст | Официальное название SaaS |
| Вендор | Текст | Компания-разработчик |
| URL | Ссылка | Адрес приложения |
| Уровень риска | Enum | Критический / Высокий / Средний / Низкий |
| Бизнес-владелец | Сотрудник | ФИО и отдел |
| ИБ-ответственный | Сотрудник | ФИО |
| Типы данных | Текст | Что хранится |
| ПДн? | Да / Нет | Обрабатывает ли ПДн граждан РФ |
| Страна хранения | Текст | Страна дата-центра |
| DPA заключён? | Да / Нет / Н/Д | Статус договора |
| SSO настроен? | Да / Нет | Интеграция с IdP |
| SCIM настроен? | Да / Нет | Автопровизия |
| Дата оценки ИБ | Дата | Когда проведена оценка |
| Дата следующей ревизии | Дата | Плановый пересмотр |
| Статус | Активен / Выводится / Выведен | Текущий статус |

| Плейсхолдер | Рекомендуемые значения |
