# Руководство по применению POL-SEC-001

## Кому читать этот файл

Ответственному за ИБ или IT-руководителю, который адаптирует шаблон под свою организацию.

---

## Шаг 1 — Определите структуру группы реагирования

Самый частый вопрос: «У нас три человека в IT, какая группа?»

**Для малой команды (до 20 человек в компании):**
- Incident Commander = руководитель / CTO
- Ответственный за ИБ = системный администратор
- IT-администратор = тот же системный администратор
- Юридическая служба = внешний юрист (договор на случай инцидента)
- PR = руководитель или маркетолог

Роли можно совмещать, **кроме Incident Commander и Ответственного за ИБ** — один управляет, второй расследует.

**Для средней команды (50–200 человек):**
Добавляется выделенный сотрудник ИБ и подключаются руководители бизнес-подразделений при P1.

## Шаг 2 — Настройте канал сообщения об инцидентах

Плейсхолдер `{{КАНАЛ_СООБЩЕНИЯ}}` — ключевой. Канал должен быть:
- Постоянным (не меняется при смене ответственного за ИБ)
- Доступным 24/7 (не только в рабочие часы для P1)
- Известным всем сотрудникам

**Варианты:**

| Вариант | Подходит |
|---|---|
| Email `security@example.com` | Всем, как базовый канал |
| Telegram-канал / бот | Быстрое уведомление, удобно для P1 |
| Тикет в Jira/Tracker с шаблоном | Для команд с развитой тикет-системой |
| Телефон дежурного | Обязателен при P1 для нерабочего времени |

Для P1 рекомендуется сочетание: email + телефон или мессенджер.

## Шаг 3 — Определитесь с регуляторными уведомлениями

### Нужно ли уведомлять РКН?

Если Организация обрабатывает персональные данные (а значит, на неё распространяется ФЗ-152) — **да**, при любой утечке ПДн. Проверьте:
- Есть ли в Организации реестр ИСПДн (информационных систем персональных данных)?
- Известен ли идентификатор оператора в реестре РКН?
- Зарегистрирован ли кабинет на [pd.rkn.gov.ru](https://pd.rkn.gov.ru)?

Если ответ «нет» на любой из этих вопросов — это отдельный пробел, который нужно закрыть до инцидента, а не во время.

**Что считается «утечкой ПДн»?**
- Любой несанкционированный доступ к данным, которые идентифицируют физических лиц
- Потеря устройства с незашифрованными ПДн
- Ошибочная отправка ПДн третьей стороне
- Атака с получением дампа базы данных с ПДн

### Нужно ли уведомлять НКЦКИ?

Только если Организация является **субъектом критической информационной инфраструктуры** (КИИ) по ФЗ-187. К субъектам КИИ относятся организации из 13 сфер: здравоохранение, транспорт, энергетика, финансы, связь, оборонная промышленность и др. Если сомневаетесь — уточните у юриста.

## Шаг 5 — Проведите первую тренировку

Tabletop exercise — это разбор гипотетического сценария без реальных систем. Занимает 2–3 часа, не требует подготовки инфраструктуры.

**Три сценария для начала:**

1. **Фишинг → компрометация учётной записи менеджера с доступом к CRM** — что делаем?
2. **Шифровальщик на рабочей станции бухгалтера** — изолируем, платим или нет, уведомляем?
3. **Разработчик случайно запушил AWS-ключ в публичный репозиторий** — алгоритм действий?

По итогам тренировки зафиксируйте пробелы в процессе и обновите политику.

## Частые ошибки

### Ошибка 1: «Сначала починим, потом сообщим»
Это нарушает цепочку доказательств и может привести к пропуску срока уведомления РКН. Сообщение должно идти параллельно с сдерживанием, а не после устранения.

### Ошибка 2: Выключить сервер как первый шаг
Выключение уничтожает оперативную память, где может находиться ключ шифрования, артефакты вредоносного ПО, активные соединения. Сначала изоляция от сети, потом — решение о выключении с {{ОТВЕТСТВЕННЫЙ_ЗА_ИБ}}.

### Ошибка 3: Отсутствие внешней резервной копии логов
При инциденте атакующие часто чистят логи в системе. Если логи хранятся только локально — расследование зайдёт в тупик. Нужна централизованная система логирования ({{СИСТЕМА_ЛОГОВ}}).

### Ошибка 4: Не отличать событие от инцидента
Миллион событий в день — это норма. Задача SIEM/SOC — отфильтровать инциденты. Чёткие критерии классификации (раздел 4) помогают дежурному быстро принять решение, не эскалируя каждый алерт.

## Метрики для отслеживания

| Метрика | Целевое значение |
|---|---|
| Время до первичного отклика на P1 | < 30 минут |
| Соблюдение срока уведомления РКН (если утечка ПДн) | 100% |
| % инцидентов P1–P2 с проведённым постинцидентным разбором | 100% |
| Повторные инциденты одного типа в течение 12 месяцев | 0 (цель) |

## Связь с ISO/IEC 27001:2022

Разделы A.5.24–A.5.28 полностью покрываются этой политикой. При подготовке к сертификации используйте §5–§9 как основу для Evidence при аудите по домену управления инцидентами.
