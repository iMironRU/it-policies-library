# Руководство по применению POL-FIN-001

## Ключевые решения при внедрении

### Решение 1. Порог CAPEX (`{{ПОРОГ_КАПЕКС}}`)

Определяет, что идёт на баланс как актив, а что списывается как расход периода. Ориентиры:

- **100 000 ₽** — типичный порог для среднего бизнеса (соответствует лимиту стоимости ОС в налоговом учёте по НК РФ)
- **40 000 ₽** — минимальный порог для бухгалтерского учёта ОС по ФСБУ 6/2020
- **Единый порог для бух. и управленческого учёта** упрощает жизнь; разные пороги — дополнительная нагрузка на бухгалтерию

**Важно:** лицензии на ПО и SaaS-подписки — отдельный вопрос. По ФСБУ 14/2022 «нематериальный актив» — это исключительное право, а не лицензионный договор. Подписки (Office 365, 1С:Фреш, Salesforce) — OPEX вне зависимости от суммы. Perpetual-лицензии — зависит от учётной политики организации. Консультируйтесь с главным бухгалтером.

### Решение 2. Порог тендера (`{{ПОРОГ_ТЕНДЕРА}}`)

Сумма, выше которой обязателен конкурентный отбор. Ориентиры:

- **500 000 ₽** — разумный порог для компаний до 500 сотрудников
- **1 000 000 ₽** — для компаний 500–2000 сотрудников
- **Госкомпании и организации с госучастием** — руководствуйтесь ФЗ-223 и внутренними регламентами закупок; эта политика к ним не применима без адаптации

### Решение 3. Модель распределения затрат (§8)

| Модель | Когда применять | Плюсы | Минусы |
|---|---|---|---|
| Централизованная | IT как сервисное подразделение без P&L у бизнес-юнитов | Проще, меньше overhead | Подразделения не осознают стоимость IT |
| Show-back | Хочется прозрачности без административного overhead | Осознанность потребления | Не влияет на P&L подразделений |
| Charge-back | Бизнес-юниты имеют P&L; нужно «честное» распределение | Максимальная прозрачность; давление на оптимизацию | Сложная методология; конфликты по базам распределения |

## Лицензионный реестр: с чего начать

Большинство организаций не имеют актуального реестра. Пошаговый план создания:

1. **Сбор данных**: запросите у бухгалтерии все IT-затраты за последние 12 месяцев с разбивкой по поставщикам
2. **Инвентаризация договоров**: перечислите все действующие IT-договоры (подписки, лицензии, поддержка)
3. **Сопоставление с использованием**: для каждого продукта — сколько куплено vs сколько активных пользователей
4. **Приоритизация**: сначала закройте крупные позиции (>100 000 ₽/год), потом мелкие

**Инструменты инвентаризации:**
- Windows: Active Directory + SCCM/Intune отчёты об установленном ПО
- macOS: Jamf или аналоги
- Облако: Cost Explorer (AWS), Cost Management (Azure), billing export (GCP)
- SaaS: запрос администраторского отчёта об активных пользователях у каждого вендора

### Типичные находки при первой инвентаризации

- 20–40% лицензий Microsoft Office не использовались активно в последние 90 дней
- Подписки на инструменты уволенных сотрудников не отозваны (проблема онбординга/оффбординга — см. POL-IAM-003)
- Несколько команд купили аналогичные инструменты независимо (3 разных task tracker, 2 CRM)
- Облачные ресурсы не отключаются после окончания проектов (dev-среды, тестовые стенды)

## TCO: как считать для закупок

Для обоснования крупных IT-решений нужен TCO на 3 года. Компоненты:

| Компонент | On-premise | Cloud/SaaS |
|---|---|---|
| Приобретение | CAPEX оборудования + лицензии | Нет (или минимально) |
| Внедрение | Проектные работы, интеграция | Настройка, миграция данных |
| Эксплуатация | Электроэнергия, ЦОД, администрирование | Подписка + поддержка |
| Поддержка вендора | Техподдержка, обновления | Включено в подписку |
| Обучение | Обучение пользователей | Обучение пользователей |
| Вывод из эксплуатации | Миграция данных, утилизация оборудования | Экспорт данных |

**Распространённые ошибки в TCO:**
- Не учтена стоимость администрирования (часы IT-специалистов × ставка)
- Не учтена стоимость интеграции с существующими системами
- CAPEX vs OPEX сравнивается без дисконтирования
- Не учтён риск изменения цен вендора (особенно актуально для зарубежного ПО в условиях санкций)

## Управление облачными расходами (FinOps)

Для организаций с облачным потреблением >500 000 ₽/мес. рекомендуется выстраивать FinOps-практики:

- **Теги ресурсов**: каждый облачный ресурс тегируется (подразделение, проект, среда dev/stage/prod) — основа для показа расходов
- **Бюджетные алерты**: уведомления при достижении 80%/100% месячного бюджета по проекту
- **Rightsizing**: ежеквартальный анализ недоиспользованных ресурсов (idle VM, oversized DB)
- **Reserved instances / Savings Plans**: для стабильных нагрузок экономия 30–60% vs on-demand
- **Завершение нерабочих ресурсов**: автоматическое выключение dev/test сред в нерабочее время

## Частые ошибки

### Бюджет как ритуал

IT-директор подаёт заявку «по образцу прошлого года +10%» без анализа потребностей. CFO её урезает «на 15%». Никто не знает реальных потребностей. Результат — либо недофинансирование критичных вещей, либо перерасход на незначительные.

### Лицензии без владельца

Каждая лицензия или подписка должна иметь ответственного — человека, который отвечает за оценку нужности при продлении. Без этого продление происходит автоматически.

### TCO только для новых систем

TCO важен и для существующих систем — особенно legacy. Организация иногда продолжает платить миллионы за систему, которую дешевле заменить, просто потому что никто не считал.

### CAPEX как способ «помочь бюджету»

Перевод затрат из OPEX в CAPEX для «выполнения бюджета» — бухгалтерский приём, который создаёт будущие проблемы с амортизацией и активами. Классификация должна отражать экономическую суть, а не финансовый convenience.
